## 5. 📊 Agile-анализ (уровень CTO)

### Понимание продукта

**Частичное.** Есть общее понимание user flow (landing → auth → dashboard), но нет PRD, нет user stories, нет acceptance criteria. Продуктовые решения принимаются "на лету" во время звонков.

### Backlog

**Отсутствует.** Задачи формулируются устно и записываются в Slack plain text. Jira обещана "через пару дней". Нет приоритизации, нет estimation, нет definition of ready.

### Ownership

**Слабое.** Мила одновременно: lead, PM, ревьюер, архитектор. Команды не самоорганизованы — Orange Team пришла на митинг без плана. Задачи раздавались на звонке методом "есть добровольцы? нет? тогда ты".

### Definition of Done

**Отсутствует.** Есть чеклист для PR (Google Doc), но нет DoD для фич. Неясно: что значит "задача сделана"? Когда PR merged? Когда протестировано? Когда задеплоено?

### Синхронизация между ролями

**Проблемная.** Дизайнер (Наташа) работала параллельно, дизайн не совпал с ожиданиями Милы. Коммуникация шла через голосовые сообщения, которые не были поняты. PM отсутствует. Backend и frontend планируются устно без API-контракта.

### Что работает

- Мила чётко понимает, как должен выглядеть PR-процесс, и объясняет его.
- Demo calls — хорошая практика для visibility.
- Желание делать чистый шаблон — правильный подход.
- Есть готовый backend-шаблон (Микола).

### Что сломано

- Нет PM, нет backlog, нет Jira — разработка начинается в хаосе.
- Нет API-контрактов между frontend и backend.
- Нет CI/CD, нет тестов, нет staging.
- Задачи формулируются устно → потеря контекста.
- Одна точка отказа в ревью (Мила).

### Что нужно исправить (топ-5)

1. **Jira/backlog — немедленно.** Без трекера задачи теряются, нет accountability.
2. **API-контракты.** Прежде чем писать frontend и backend параллельно — зафиксировать endpoints, request/response schemas.
3. **Definition of Done** для каждой задачи. Хотя бы: code done + PR merged + manual QA passed.
4. **CI pipeline.** Линтер + билд на каждый PR. Без этого PR review превращается в ручную проверку кода.
5. **Документация решений.** Всё, что обсуждается на звонках, должно фиксироваться в wiki/confluence/notion.

### Технологии (подтверждённые)

- **Frontend:** React, Redux (slices/reducers), CSS modules/styled (aliases)
- **Backend:** Node.js
- **Auth:** JWT (Magic Link, passwordless)
- **Email:** Nodemailer (рекомендация)
- **Hosting:** Hetzner
- **Containerization:** Docker
- **VCS:** GitHub, PR-based workflow

### Технологии (не определены / неясны)

- **Database:** не обсуждалась (нужна для users + tokens)
- **ORM:** не обсуждалась
- **API format:** REST предположительно, нет спецификации
- **Frontend state management:** Redux Toolkit (есть slice), но детали неясны
- **Testing:** не упоминалось
- **CI/CD:** не упоминалось

### Потенциальные архитектурные проблемы

1. **Email через Gmail SMTP с логин/паролем** — не production-ready. Нужен сервис (SendGrid, AWS SES, Resend) для масштабирования и deliverability.
2. **Нет refresh token механизма** — обсуждался только JWT, но не его lifecycle (expiry, refresh, revocation).
3. **Нет middleware для auth** — непонятно, как будут защищены dashboard endpoints.
4. **Нет API-контракта** — frontend и backend пишутся параллельно без swagger/openapi.

## 7. 🎯 Что делать мне (как разработчику)

### Конкретные действия для максимального роста

**1. Стань тем, кто документирует.**
После каждого звонка — пиши summary в Slack (кто что делает, что решили). Мила перегружена и оценит это. Это создаёт visibility и показывает ownership. Никто в команде этого не делает — ты будешь единственным.

**2. Предлагай API-контракты до написания кода.**
Перед началом таски напиши в Slack: "Я планирую сделать endpoint POST /auth/magic-link, request: {email: string}, response: {success: boolean}. Подтвердите?" Это middle-level мышление. Мила буквально ждёт инициативы.

**3. Делай PR чаще, чем просят.**
Мила сказала "каждые 2–3 дня". Делай каждый день. Маленькие PR проще ревьюить, быстрее мержатся, больше visibility. Добавь чеклист из Google Doc.

**4. Добавь линтер и prettier в проект.**
Если в шаблоне нет ESLint + Prettier — добавь и создай PR. Это 30 минут работы, но это показывает engineering culture. Мила явно ценит чистоту кода.

**5. Изучи и предложи email-сервис.**
Если тебе досталась или смежна задача с email — не делай через Gmail пароль. Изучи SendGrid free tier или Resend, предложи Миле. Это senior-решение, которое выделит тебя.

**6. Пиши тесты первым.**
Никто не упомянул тесты. Если ты добавишь хотя бы unit-тесты на свою часть — это будет заметно. Jest для backend, React Testing Library для frontend.

**7. Ставь reaction на каждый комментарий Милы.**
Она буквально просила об этом. Мелочь, но показывает внимательность. Если не согласен — аргументируй со ссылками.

**8. Не жди, пока тебе дадут задачу.**
На звонке было "есть добровольцы? нет? тогда назначаю". Будь тем, кто берёт задачу первым. Выбирай задачи с backend + frontend overlap — это даёт fullstack опыт.

### Ошибки, которых нужно избежать

- **Молчание на звонках.** Мила ценит обратную связь. Задавай вопросы, предлагай решения.
- **PR без чеклиста.** Это первое, что Мила будет проверять.
- **Работа без develop branch.** Мила предупредила о последствиях — она серьёзно.
- **Захардкоженные значения.** Она это ненавидит — вынеси в env/config.
- **Ожидание идеального дизайна.** Начинай с того, что есть, уточняй по ходу.
