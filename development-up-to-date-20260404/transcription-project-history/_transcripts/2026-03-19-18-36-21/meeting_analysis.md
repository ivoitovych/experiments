### Блок 5: Проект — Data Anonymization System

Компания работает с healthcare-проектами. Ключевая особенность — большое количество регуляций.

**Суть проекта:** Создать систему анонимизации данных пациентов.

- Входные данные: медицинские данные пациентов (имена, адреса, диагнозы, лекарства и т.д.).
- Система определяет чувствительные данные (patient ID, SSN, имя) и подсвечивает их.
- Пользователь выбирает, какие данные анонимизировать.
- Анонимизация = замена реальных данных на фейковые (mock data).
- Генерируется шаблон, определяющий, где должны быть mock-данные.
- На выходе — структурно валидные данные, но без привязки к реальным пациентам.
- Цель: подготовить данные для обучения AI без нарушения приватности.

**Регуляции (compliance):** HIPAA (США), GDPR (Европа), CCPA, и другие.

Дополнительно: будут лендинги, дашборды, система логина, графики.

### Блок 7: Git Workflow

1. Один человек от каждой команды настраивает шаблон (frontend + backend).
2. Настройка делается в **master** ветке.
3. После ревью и одобрения куратором создаётся ветка **develop**.
4. **Master закрыт навсегда** до финального релиза.
5. Вся работа ведётся от **develop**: создаёте feature-ветку → работаете → пушите → создаёте Pull Request.
6. **Никогда не пушить напрямую в develop.** Всегда через PR.

### Блок 8: Правила PR и Code Review

**Для frontend PR:**
- Обязательно прикреплять скриншот UI-изменений.

**Для backend PR с изменениями БД:**
- Обязательно прикреплять схему базы данных (DBeaver, phpMyAdmin и подобные инструменты генерируют это автоматически).

**Общие правила кода:**
- Try-catch для асинхронных операций.
- Никаких magic numbers — используйте константы.
- Никаких `console.log` в коммитах.
- **Никогда не коммитить `.env` файл** — это критическая ошибка безопасности, и удалить из git-истории крайне сложно.
- Должен быть `.env.example`.
- Правильно настроить ESLint (единообразно для всей команды).
- PR должен содержать чеклист.

Невыполнение правил PR — блокер: куратор отклонит PR, и вы станете бутылочным горлышком для команды.

## 5. 📊 Agile-анализ (уровень CTO)

### Есть ли понимание продукта?

**Частично.** Куратор дала высокоуровневое описание: это система анонимизации медицинских данных для обучения AI. Есть Figma, видео, документ с правилами валидации. Но детальное понимание ещё не сформировано — на это отведена следующая неделя.

### Есть ли backlog?

**Нет.** Бэклога нет. Его создание — задача команды (PM + разработчики) на подготовительную неделю. Это и риск, и возможность проявить инициативу.

### Есть ли ownership?

**Нет.** Роли не распределены. Нет тех-лида, нет явного PM-лида. Команда должна самоорганизоваться. Куратор осознанно не назначает — ждёт, что это произойдёт органически.

### Есть ли Definition of Done?

**Частично.** Для PR есть: скриншот (FE), схема БД (BE), чеклист, соблюдение код-стайла. Для фич и спринтов — нет. Нужно определить самим.

### Есть ли синхронизация между ролями?

**Нет.** Команда ещё не знакома. Первый внутренний звонок ещё не состоялся. Дизайнер, PM и 5 разработчиков пока не синхронизированы.

### Вердикт

| Аспект | Статус |
|--------|--------|
| **Что работает** | Чёткие правила PR/git, понятный tech stack, конкурентная модель между командами, осознанный менторский подход |
| **Что сломано** | Нет бэклога, нет ownership, нет DoD на уровне фич, команда не знакома, нет архитектурного плана |
| **Что нужно исправить немедленно** | 1) Провести звонок команды. 2) Определить роли и ответственных. 3) Создать бэклог на основе Figma и видео. 4) Договориться о DoD для фич. 5) Согласовать UI-библиотеку и архитектурные подходы |

## 6. 🧱 Архитектура проекта (System Design)

### Что известно из транскрипта

```
┌──────────────────────────────────────────────────────────┐
│                      Frontend (React)                     │
│  - Redux Toolkit (state management)                       │
│  - MUI / Styled Components (UI)                           │
│  - Landing pages, Dashboard, Login, Anonymization UI      │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTP (REST API предположительно)
┌───────────────────────▼──────────────────────────────────┐
│                   Backend (NestJS)                         │
│  - TypeORM                                                │
│  - Auth module (login/registration)                       │
│  - Compliance engine (HIPAA/GDPR/CCPA rule sets)          │
│  - Sensitive data detector                                │
│  - Anonymization / Mock data generator                    │
│  - Dashboard / Analytics API                              │
└───────────────────────┬──────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────┐
│                    MySQL Database                          │
│  - Users, Roles, Auth tokens                              │
│  - Patient data (source)                                  │
│  - Anonymization rules / templates                        │
│  - Anonymized output data                                 │
│  - Audit logs (compliance requirement)                    │
└──────────────────────────────────────────────────────────┘
```

### Ключевые модули (восстановленные из описания)

1. **Auth Module** — логин, регистрация, управление сессиями.
2. **Data Import** — загрузка / подключение к источнику данных пациентов.
3. **Compliance Selector** — выбор применимого стандарта (HIPAA, GDPR, CCPA).
4. **Sensitive Data Detector** — на основе выбранного compliance определяет чувствительные поля и подсвечивает их.
5. **Anonymization Config** — пользователь выбирает, какие из подсвеченных полей анонимизировать.
6. **Template Generator** — создаёт шаблон с маркерами, где нужны mock-данные.
7. **Mock Data Generator** — заполняет шаблон фейковыми, но валидными данными.
8. **Export / Output** — выдаёт финальный анонимизированный датасет.
9. **Dashboard** — визуализация (графики, статистика).
10. **Landing Pages** — маркетинговые / информационные страницы.

### Потенциальные архитектурные проблемы

- **Нет упоминания валидации mock-данных** — замена имени на "John Doe" просто, но замена диагнозов и лекарств требует медицинского контекста.
- **Нет информации о масштабе данных** — batch processing или real-time? Для больших объёмов нужна очередь задач.
- **Не определён формат входных данных** — CSV? JSON? Прямое подключение к БД?
- **Audit trail** — для HIPAA обычно требуется журнал аудита всех действий с данными. Не упомянут.
- **Тестирование анонимизации** — как проверить, что данные действительно анонимны? Нет re-identification attack тестов.

### Рекомендуемая архитектура (как senior)

Предложил бы разбить backend на модули NestJS:

```
src/
├── auth/           — JWT, guards, login/register
├── users/          — user CRUD, roles
├── compliance/     — rule sets per standard (HIPAA, GDPR, CCPA)
├── data-import/    — file upload, parsing (CSV/JSON)
├── detection/      — sensitive field detection logic
├── anonymization/  — template generation + mock data filling
├── export/         — output generation (CSV/JSON)
├── dashboard/      — aggregation queries for charts
└── common/         — DTOs, decorators, pipes, interceptors
```

Frontend — feature-based structure:

```
src/
├── app/            — store setup, routing
├── features/
│   ├── auth/
│   ├── dashboard/
│   ├── anonymization/
│   │   ├── components/
│   │   ├── hooks/
│   │   └── slice.ts
│   └── landing/
├── shared/         — UI kit, utils, API client
└── types/
```

| **Документировать решения** | Никто этого не делает на стажировках — это сразу выделяет | Куратор видит зрелость мышления |
| **Предлагать решения, а не задавать вопросы** | Главный оцениваемый навык — проактивность | "Я попробовал X, но столкнулся с Y, планирую Z" vs "что делать?" |

### Ошибки, которых нужно избежать

1. **Ждать, пока кто-то скажет, что делать.** Куратор прямо сказала — она не будет навигировать. Если вы ждёте — вы теряете время и баллы.
2. **Работать в одиночку.** Teamwork — навык №1. Даже если вы сильнее, помогите другим.
3. **Игнорировать PR-правила.** Первые 2 недели — самое критичное время по PR. Каждый отклонённый PR — задержка для всей команды.
4. **Push в develop без PR.** Куратор буквально сказала: "don't be that person".
5. **Коммитить .env.** Один коммит — и секреты навсегда в git-истории.

### Стратегия: junior → middle mindset

- **Junior** спрашивает "что делать?". **Middle** приходит с планом и точечными вопросами.
- **Junior** делает свою задачу. **Middle** думает о том, как его код влияет на других.
- **Junior** ждёт ревью. **Middle** ревьюит чужой код и даёт конструктивный фидбек.
- **Junior** фиксит баги. **Middle** предотвращает их (ESLint, типизация, тесты).
- **Junior** работает с кодом. **Middle** работает с системой (архитектура, data flow, edge cases).
