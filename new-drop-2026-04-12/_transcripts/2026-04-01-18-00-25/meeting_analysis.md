## 5. Agile-аналіз (рівень CTO)

### Є розуміння продукту?

**Частково.** Команда розуміє окремі компоненти (дашборд, лендинг, авторизація, анонімізація), але немає артикульованого product vision. Ніхто не згадує user stories, бізнес-цілі або метрики. Рішення приймаються "знизу вгору" — від технічних задач, не від потреб продукту.

### Є backlog?

**Формально — так, фактично — ні.** PM-дошка існує, але тімлід сама визнає, що вона не актуальна. Таски створюються прямо під час мітингу. Немає пріоритизації, story points, definition of ready.

### Є ownership?

**Слабкий.** Ігор не розумів, що має робити. Марк працював автономно (добре), але заблокований інфраструктурою. Олександр чекає дизайн. Тімлід — єдиний джерело правди.

### Є definition of done?

**Ні.** Немає критеріїв завершення задач. PR-и в review без чітких чеклістів. Немає code review-процесу (окрім approve від тімліда).

### Є синхронізація між ролями?

**Мінімальна.** Дизайнер працює окремо. Бекенд і фронтенд синхронізуються лише на мітингу. Немає спільних контрактів (API-специфікації).

### Що працює

- Тімлід активно координує, бере на себе відповідальність
- Марк проявляє ініціативу — сам знайшов рішення при блокері
- Мобільна адаптація Ігната зроблена якісно
- Є код-рев'ю процес (хоча б базовий)

### Що зламано

- Backlog — створюється на ходу під час мітингу
- Бранч-стратегія — розробники працюють з різних гілок, конфлікти накопичуються
- Onboarding — новим людям немає інструкцій (Docker, `.env`, запуск)
- Дизайн-процес — дизайнер асинхронна, немає handoff-процесу

### Що потрібно виправити (негайно)

1. **README з інструкцією запуску** — Docker, `.env`, бази, міграції
2. **Єдина develop-бранча** — примусовий merge всіх feature-бранчів
3. **Backlog grooming** — перенести всі задачі в трекер ДО мітингу
4. **API-контракти** — зафіксувати endpoints до початку інтеграції фронт + бек
5. **Definition of Done** — код зібрався, пройшов review, задеплоєний на dev-середовище

### Технології (встановлені)

- **Frontend:** React (або аналог), responsive (мобільна адаптація є)
- **Backend:** NestJS (модульна архітектура, Swagger для API)
- **Database:** MySQL
- **Auth:** Magic Link (email + JWT-token)
- **Anonymization:** Microsoft Presidio (планується)
- **DevOps:** Docker (конфіг втрачений, відновлюється), Git
- **Інструменти:** Husky (git hooks), Fireflies (запис мітингів)

### Зовнішні залежності

- **InvestiGate** — зовнішній endpoint, потрібно розібратись, як працює
- **Presidio** — потрібні доступи до сервера для сетапу
- **Дизайн (Figma)** — Наташа, асинхронна робота

### Потенційні проблеми архітектури

1. **Немає API-контрактів** — фронтенд і бекенд розробляються без узгодженого інтерфейсу
2. **Немає CI/CD** — не згадується жодний pipeline, деплоймент-процес
3. **Немає `.env.example`** — кожен налаштовує середовище вручну
4. **Docker — єдина точка запуску** — видалений конфіг заблокував половину команди
5. **Presidio як зовнішній сервіс** — потребує окремого хостингу і мережевої зв'язності

## 7. Що робити мені (як розробнику)

### Конкретні дії для зростання

**1. Стань тим, хто знімає блокери**

Зараз найбільший блокер — відсутність Docker-конфігу та `.env`. Якщо це твоє завдання — зроби його ідеально: Dockerfile, docker-compose, `.env.example` з коментарями, README з інструкцією запуску за 5 хвилин. Це зробить тебе незамінним.

*Чому важливо:* Тімлід буквально сказала, що це блокер для всієї команди. Хто зніме блокер — того запам'ятають.

**2. Навчися працювати з конфліктами Git як профі**

Це прямо зараз pain point команди. Вивчи `git merge`, `git rebase`, `git rerere`. Якщо зможеш допомогти іншим резолвити конфлікти — це сильний middle-сигнал.

*Як це вплине:* Тімлід сама каже "конфлікти — стандартна тема". Той, хто їх не боїться — виглядає надійно.

**3. Проактивно документуй**

Ніхто в команді не пише документацію. Створи README, опиши API-endpoints через Swagger, зафіксуй архітектурні рішення. Це те, що відрізняє junior від middle.

*Конкретно:* Після кожного мітингу — фіксуй рішення в wiki/notion. Запропонуй `.env.example`, `CONTRIBUTING.md`.

**4. Не чекай — запитуй і пропонуй**

Ігор не розумів свої завдання і мовчав. Це антипаттерн. Якщо щось не зрозуміло — запитай одразу. Якщо бачиш проблему — запропонуй рішення.

*Формула:* "Я бачу проблему X. Пропоную рішення Y. Якщо ок — зроблю за Z часу."

**5. Закривай таски повністю**

Зроби не просто "працює локально", а: код написаний → тести є → PR створений → конфлікти вирішені → опис в PR зрозумілий → готовий до review.

*Чому:* Тімлід перевантажена. Кожна задача, яка приходить "готова" без додаткових питань — знімає з неї навантаження.

**6. Пропонуй покращення процесів**

- "Давайте додамо `.env.example` в репо?"
- "Може зробимо шаблон для PR?"
- "Я можу оновлювати борд після кожного мітингу?"

*Чому:* Це показує mindset middle+ — мислення не тільки про свій код, а про ефективність команди.

### Помилки, яких не допускати

- **Не працюй з "неправильної" бранчі** — це вже проблема Ігоря, не повторюй
- **Не мовчи, коли заблокований** — пінгуй одразу
- **Не роби великі PR** — краще малі, часті, легкі для review
- **Не ігноруй конфлікти** — мержи develop у свою бранчу щодня
- **Не роби без таски** — навіть якщо "домовились усно", створи таску сам
