# History

A chronological record of how the project got to where it is. Read
this if you want to know *what happened*; read `PROCESS.md` for *how
we work* and *why the conventions exist*; read `STYLE.md` for *what
the conventions are*. The three files complement each other and do
not duplicate.

This log covers the period from the first commit through the
completion of Chapter 4's review cycle and the establishment of the
tooling and process baseline.

---

## Phase 0 — Project bootstrap

The repository was opened with an empty commit on branch
`claude/init-quantum-computing-iaiRN` to start a clean writing space
for *Quantum Computing for Experienced Developers — A Structured
Guide from Core Principles to Modern Practice*.

Source materials in place at the start: `INSTRUCTIONS.md` (author-identity
and commit rules), `TOC.md` (697 lines, 13 parts,
37 chapters), and `BookDescription.md` (385 lines, the book charter).
These three pre-existing files defined the target shape and tone.

### Licensing decision

Choosing a license preceded any substantial writing. Goals: free for
non-commercial and private use, mandatory attribution, royalties owed
to the author if the work is printed or sold. After surveying the
options, the project settled on **Creative Commons Attribution-
NonCommercial-NoDerivatives 4.0 (CC BY-NC-ND 4.0)** for the
non-commercial path, plus a separately-negotiable commercial license.
The `LICENSE` file at the repo root reflects both layers.

### File-scope decision

Three layouts were considered: per-section (~250+ files,
too fragmented for navigation and link hygiene), per-part (13 files,
too large for diff review and forward-reference clarity), and
per-chapter (45 files: 37 chapters + 3 front-matter + 5 appendices).
**Per-chapter** was chosen as the best compromise between
manageability and reading flow, and is now the structural premise of
every tool and convention in the repository.

### Render-target decision

GitHub-native rendering is the primary target: math renders in the
GitHub web viewer without a build step, and the repository becomes the
canonical reading surface. mdBook and Pandoc compatibility is
maintained as a secondary target by avoiding renderer-specific LaTeX
features and macros. This decision is the reason for many of the
notational rules in `STYLE.md` (raw `\langle`/`\rangle` Dirac
notation, no `physics` macro package, no `\newcommand`).

## Phase 1 — Scaffolding and tooling baseline

Once the structure was settled, the directory tree and 45 stub files
were generated by `scripts/scaffold.py`. Every stub starts with a
**status block** of the form

```
> **Status:** stub · **Phase:** N · **Sections drafted:** 0 / M
```

with five lifecycle states `stub` → `outlined` → `draft` → `reviewed`
→ `final`. `PROGRESS.md` is generated from these blocks by
`scripts/generate_progress.py`, so editing the status of any chapter
and re-running the script updates the project's progress page
deterministically.

Phases are the writing order (not the reading order): chapters that
share prerequisite material are grouped so that each new chapter can
lean on already-drafted prerequisites instead of forward references.
The phase mapping lives in `scripts/phases.py` as a single source of
truth that the scaffold and progress scripts both import.

`tools/lint.py` was added at the same time with structural and
notational invariants: every chapter file must have a top-level
heading, a status block, and a Table-of-Contents link; relative links
must resolve; and forbidden physics-package macros (`\ket{}`, `\bra{}`,
`\braket{}`) are rejected. The lint runs in well under a second and
became the first guard rail.

`STYLE.md` was written alongside the scaffold and captured the
conventions for file layout, per-chapter structure, math notation, and
Markdown rules.

A small `__pycache__/` slip-up early on prompted the addition of
`.gitignore` rules covering Python artifacts, OS/editor files, and
generated build directories.

## Phase 2 — Drafting Chapter 4

Chapter 4 (*Mathematical Background for Quantum Computing*) was
chosen as the first drafted chapter because of its foundational role:
every later chapter inherits its conventions, notation, sanity-check
format, and tone. The initial draft (`4e566d1`) covered 13 sections
spanning complex amplitudes, vector spaces, inner products, operators,
spectral decomposition, tensor products, change of basis, Hilbert
spaces, Dirac notation, Fourier/QFT, and a probability/information
preview.

What followed was thirteen rounds of substantive review and revision.

## Phase 3 — The review-loop arc

The review loop on Chapter 4 produced a recognisable pattern that now
informs how later chapters should be approached.

### Rounds 1–2: substantive corrections

Real factual gaps surfaced. The original Holevo-bound statement was
wrong (it stated a single-density-matrix bound; the correct statement
is an ensemble bound involving the Holevo quantity `χ = S(ρ) − Σ p_x
S(ρ_x)`). "Every quantum gate is unitary" was too absolute; the
proper qualification is the *ideal closed-system circuit model*,
acknowledging measurement, reset, noise, and channels as non-unitary
operations. The chapter's QFT-complexity discussion conflated gate
count, depth, and FFT comparison. SVD and positive-semidefinite
operators were missing entirely.

Rounds 1–2 fixed those gaps. By the end of round 2 the chapter had a
new SVD section, PSD treatment in §4.5, properly stated Holevo, and
sanity-check blockquotes after the heaviest sections.

### Round 4: structural reorder

A reviewer noticed that Schmidt decomposition was being introduced in
SVD before tensor products had been formally defined — pedagogically
inverted. Sections §4.8 (SVD) and §4.9 (Tensor Products) were swapped
so that composite-system structure is established before SVD's
Schmidt-decomposition application of it.

### Rounds 5–9: precision and convention

These rounds dealt with wording, naming, and qualifiers:

- "distinct eigenvalues" → "distinct spectral values" to avoid the
  "non-degenerate" reading.
- "accessible information" tightened to mean the supremum over
  measurements, with the per-measurement `I(X; Y)` bound stated
  separately.
- The post-measurement Born-rule formula explicitly requires the
  outcome to have actually occurred (`⟨ψ|Pλ|ψ⟩ > 0`).
- Active-vs-passive basis change clarified with explicit examples.
- Qiskit ordering warnings rewritten to distinguish the four
  conventions (circuit-diagram order, integer interpretation, printed
  bit-string order, statevector-index order).
- `Convention QFT-sign-minus` named so later algorithm chapters can
  reference it by name.

### Round 10: a real omission

After nine rounds, a reviewer flagged a structural gap that the
preceding nine had missed: **commutators and simultaneous
diagonalization** had never been introduced. `[A,B] = AB − BA`, the
Pauli commutation relations, and the "commuting normal operators
share an eigenbasis" fact are referenced implicitly by later chapters
(Hamiltonian simulation, Trotterization, Pauli algebra, compatible
observables, QAOA, QEC) but had no home in Chapter 4. A new
subsection was added at the end of §4.5.

This round became the project's reference point for "polish-grade
review still occasionally surfaces real omissions; foundational
chapters are worth iterating even past the polish threshold."

### Rounds 11–13: terminology and missing formulas

The remaining rounds were almost entirely polish — softer
"pairwise commuting" wording, "Schmidt spectrum is the raw data
from which measures are derived" rather than "determines every
measure", `min(m, n)` qualifier on SVD singular-value count,
`L²(ℝ)` qualified as "for example ... for one continuous degree of
freedom", `Hilbert space` redefined as "appropriate to the
register being discussed" rather than literally `ℂ^(2^n)`
everywhere.

Round 13 surfaced four genuinely missing formulas: tensor-product
inner product and norm, the explicit `n`-qubit expansion
`|ψ⟩ = Σ_x α_x |x⟩`, the rank-one Born rule for nondegenerate
orthonormal-basis measurement, and the matrix-exponential bridge
(`e^A = Σ A^k/k!` and the spectral form `e^A = Σ e^{λᵢ} Pᵢ`). The
Bell-state SVD example was added as a worked link between §4.8 and
§4.9.

## Phase 4 — Discovering the GitHub-Markdown gotcha family

The most expensive lesson from drafting Chapter 4 was that GitHub's
Markdown processor unescapes a layer of backslashes (and applies
several other quirks) *before* MathJax sees the math. Five gotchas
surfaced one by one, each from a real render-time bug:

1. **`\\` row breaks** (`9171e6b`, `7471078`). 2×2 Pauli matrices and
   the standard basis vectors `|0⟩ = (1, 0)ᵀ` rendered as row vectors.
   Source `\\` needs to be `\\\\` to survive the unescape pass.

2. **`\{` and `\}` set braces** (`7471078`). `\{0,1\}^n` rendered as
   `0,1^n` with no visible braces. Source needs `\\{` / `\\}`.

3. **`\,` thin space** (`212a077`). `\overline{u_i}\, v_i` rendered
   as `ū_i, v_i` with a literal comma. Source needs `\\,`.

4. **`\|` norm bar** (`d996244`). Every vector or operator norm
   collapsed to a modulus bar — `\|v\|` rendered as `|v|`,
   destroying the chapter's careful single-bar/double-bar distinction.
   Source needs `\\|`.

5. **`$$ ... $$` inside blockquotes or list-item continuations**
   (`55a4c40`). The entire equation rendered as literal `$$` text.
   No backslash trick fixes this one — the equation has to be pulled
   *out* of the `>` block or list continuation and rewritten as a
   plain bold-prefixed paragraph.

`tools/lint.py` grew a math-block scanner that detects each pattern
in source. The lint rules pay for themselves on every commit — when
later edits introduced new `\,` instances they were caught
immediately, and the round-12 `$$`-in-blockquote rule fired on
fresh content as soon as it was added.

`PROCESS.md` now records each gotcha with symptom, cause, and fix
under "Known renderer gotchas" so the institutional memory survives
context loss.

Related but separate: `\operatorname{}` was discovered (early on, in
`9171e6b`) to be disallowed entirely by GitHub's MathJax
configuration, prompting a switch to `\mathrm{}` for `\mathrm{tr}`,
`\mathrm{Var}`, etc.

## Phase 5 — Screenshot review pipeline

Source-level lint catches what it can catch from source. Some
rendering bugs are only visible in the rendered output. Several of
the gotchas above (`\|`, `$$`-in-blockquote, an early `\operatorname`
case) were caught only because the user opened the rendered chapter
in GitHub and screenshotted it manually.

To make that loop cheaper:

- `tools/screenshots.py` (`35d59ae`) was added — a Playwright Python
  script that drives a real headless Chromium against the GitHub blob
  URL for a given commit and writes per-section PNGs under
  `.artifacts/screenshots/<short-sha>/<chapter-slug>/`. The math wait
  is permissive (any of `mjx-container`, `g-math`, `<math>`, or
  `.katex`) with a fallback delay so the script always produces
  screenshots rather than hanging.

- The `Makefile` (`73bee81`) bundles `make setup`, `make lint`,
  `make progress`, `make screenshots CHAPTER=...`, and
  `make clean-artifacts` so the venv activation step doesn't have to
  be remembered. `make setup` is idempotent via a sentinel file
  (`.venv/.installed`).

- The `19d43bc` follow-up added missing-prereq detection in the
  Makefile (Ubuntu 24.04 ships without `python3-venv` by default;
  detect the missing `ensurepip` and print the apt command to install
  rather than failing cryptically) and made the screenshot script
  tolerant of unknown MathJax markup so a render that finishes
  faster or slower than expected still yields usable PNGs plus a
  diagnostic.

- The screenshot artifacts themselves are not committed. They live
  under `.artifacts/screenshots/` which is gitignored. When a review
  pass needs to be shared, the commit-on-a-throwaway branch pattern
  (`git checkout -b review/...; git add -f .artifacts/...;
  git push; ... git push --delete review/...`) keeps the work
  branch clean.

## Phase 6 — Institutional memory

After nine review rounds it was clear that the project's accumulated
knowledge — review-loop discipline, the renderer-gotcha catalog, the
file-scope and license decisions — lived only in conversation
history. The risk of losing it on a context reset or a long pause
prompted the creation of `PROCESS.md` (`f6b8acb`):

- *Working method*: status-block lifecycle, phase-ordered drafting.
- *Review loop*: substantive → precision → polish progression and
  the signal to freeze.
- *Toolchain*: every tool with its Make target.
- *Screenshot workflow*: the four-tier artifact table and the
  per-chapter loop.
- *Known renderer gotchas*: an annotated catalog with the story
  behind each lint rule.
- *Decision log*: dated, append-only.
- *Lessons learned per chapter*: one retrospective per chapter on
  status transition to `reviewed` / `final`.

`PROCESS.md` complements but does not duplicate `STYLE.md`. `STYLE.md`
says what the conventions are; `PROCESS.md` says how and why.

- `community/community#122438` (May 2024) — comprehensive case,

Rather than file a duplicate, an upstream comment confirming the bug

`docs/upstream-feedback/community-122438-comment.md`. A companion

## Phase 8 — The renderer-bug investigation pass

The previous phases solved the "what does Chapter 4 say" problem
well. They solved the "what does GitHub actually render" problem
badly — the gotcha catalog was assembled bug by bug from individual
screenshot accidents, the corresponding lint rules accumulated as
each bug was caught, and successive rounds of advice drifted in
different directions because nobody had laid out the bug surface
*systematically*.

The trigger to do that systematically was direct. After round 13
the chapter was claimed "verified visually" and the bug catalog
treated as authoritative. The user then produced screenshots
showing both a §4.13 `Sanity check` block and a §4.14 numbered list
rendered as literal LaTeX source — and asked "Do you feel the
aroma of bullshit?" That was the right question. Several earlier
diagnoses were based on a single failing example each, not on the
underlying pattern.

### 8.1 The structured test sheet

`docs/render-tests/math-context-matrix.md` (`5df99ae`) is the
artifact that fixed this. It enumerates 11 *containers* (top level,
`>` blockquote, bulleted list inline, bulleted list continuation,
numbered list inline, numbered list continuation, nested list,
table cell, `<details>` block, blockquote-inside-bullet,
bullet-inside-blockquote) times 10 *math forms* (simple inline,
inline `pmatrix`, inline `\\\\` outside `pmatrix`, inline thin
space, inline set braces, inline norm bar, display single-line,
display multi-line, display `pmatrix`, display `aligned`) — every
cell labelled A1…K4 so the test outputs can be reported as a list
of broken labels rather than as prose.

Rendering this sheet on GitHub immediately overturned two earlier
diagnoses and added a new bug:

- **Inline `pmatrix` is broken in every container** (`066f47d`).
  A2, B2, C2, D2, E2, F2, G2, H2, J2, K2 *all* render
  `$ A = \begin{pmatrix}...\end{pmatrix} $` as literal LaTeX. The
  §4.4 sanity-check `Q`-matrix that was blamed on the surrounding
  blockquote, and all five §4.5 inline Pauli/Hadamard/phase matrices
  that the round-13 visual review had claimed were rendering, were
  actually broken because of the inline-math parser, not the
  containers.
- **Multi-line `$$...$$` inside a plain `>` blockquote actually
  works.** B7, B8, B9, B10 all rendered correctly. The earlier
  "$$ in blockquote does not enter math mode" rule was wrong; the
  original §4.13 break was almost certainly caused by an equation
  continuation line beginning with `+` (Section L of the test sheet
  tests this hypothesis directly), which Markdown reads as a list
  marker and which therefore breaks math mode inside the blockquote
  — not the blockquote itself.
- **Norm bars `\\|v\\|` collapse to single bars `|v|` inside
  Markdown table cells.** H6 caught this; the `|` characters in
  `\\|` conflict with the table column separator. Not previously
  recorded.

### 8.2 Source-level fixes propagated from the new map

`066f47d` followed the new evidence into the manuscript:

- §4.4 sanity check: the `Q`-matrix is now display math inside the
  same blockquote (we know display-in-blockquote works).
- §4.5 sanity-check list: the five inline Pauli/Hadamard/phase
  matrices were moved out of the bullet list into two preceding
  display blocks. The bullet list now describes properties by name.
- §4.8 Bell-state sanity check: the coefficient-matrix inline
  `pmatrix` was promoted to display math inside the blockquote.
- §4.9 Schmidt example: the inline `pmatrix` was avoided entirely
  by writing `C = (1/\sqrt{2})\, I` — the scaled identity reads
  better than the explicit 2×2 in that context anyway.

`tools/lint.py` was simultaneously corrected: the over-broad
"blockquote `$$`" rule was removed, the indented-list-continuation
case kept, and a new `check_inline_pmatrix` rule added so that any
`$...\begin{pmatrix}...$` is caught at source level. Five rules
total, each now backed by a specific cell in the test sheet.

### 8.3 Single source of truth: the canonical bug memo

`docs/github-markdown-math-bugs.md` (`e8ef21d`) collects everything
the project knows about GitHub Markdown + MathJax renderer bugs
into one authoritative file, cell-by-cell justified against the
test sheet. Five bugs:

1. Markdown unescapes one layer of backslashes in math contexts
   (the `\\`, `\{`, `\}`, `\,`, `\|` family).
2. Inline `pmatrix` in every container.
3. Display math inside an indented list-item continuation.
4. Plain-blockquote `$$` is fine *except* when a continuation line
   starts with a Markdown list marker — hypothesis pending Section
   L confirmation.
5. Norm bars collapse to single bars inside Markdown table cells.

`PROCESS.md`'s previous "Known renderer gotchas" section was 170
lines of bug stories that had grown round by round and partly
contradicted itself. It was trimmed to a 23-line pointer at the
memo plus a five-step discipline for keeping the memo / lint / test
sheet in lockstep when new bugs surface. `tools/lint.py`'s header
comment was also rewritten to cite the memo as the source of truth
for each rule.

### 8.4 Upstream-feedback artifacts rewritten against the memo

`docs/upstream-feedback/community-122438-comment.md` and
`community-122438-howto.md` (`1121b7a`) had been drafted before the
test sheet existed and reflected the old diagnosis. Both were
rewritten:

- The new comment cites the test sheet URL as a single-page
  reproducer, enumerates the three confirmed bugs not covered by
  existing Discussions, and corrects the record on
  blockquote-`$$` (which the existing Discussion claims is broken
  and which the test sheet says works under the current renderer).
- The new howto explains what `community/community #122438` and
  `#16958` cover and what they do not, and argues — with a
  non-duplicate-filing rationale — that the inline-`pmatrix` bug
  is universal enough and unaddressed enough by existing
  Discussions to deserve a focused new Discussion of its own. The
  title / category / body for that new Discussion is sketched in
  the howto so the user can post it from the web UI or via
  `gh api graphql`.

### 8.5 Faster loop: gist-based reproducer

`tools/render-gist.py` (`c3f075a`) replaces the previous
"edit → commit → push → open GitHub → screenshot manually" loop
with `make render-gist FILE=<file.md>`: create a secret GitHub Gist
from the file, drive headless Chromium against it, capture per-H2
screenshots, then delete the gist. No commit noise on the working
branch; sub-30-second iteration once the venv is warmed.

Whether `gist.github.com` renders math identically to
`github.com/owner/repo/blob/<sha>/...` is the open question that
the first run of this tool will answer; the script's math-wait
diagnostic prints clearly enough to distinguish the two cases.

### 8.6 Portability hardening on a fresh WSL Ubuntu 24.04

The user ran the new pipeline against a fresh WSL Ubuntu 24.04
clone and surfaced two real environment gaps that the existing
setup did not handle:

- `playwright install chromium` succeeds, but a minimal Ubuntu /
  WSL install does not ship the system libraries Chromium needs to
  launch (`libnspr4`, `libnss3`, `libdbus-1-3`, `libatk*`, ...).
  The binary failed at launch with `error while loading shared
  libraries: libnspr4.so`.
- `tools/render-gist.py` was deleting the gist in a `finally`
  block, so the capture failure also destroyed the artifact the
  user would have wanted to look at manually.

`64d3b53` addressed both:

- New Makefile target `make setup-system-deps` wraps
  `sudo playwright install-deps chromium` (one-time, sudo prompt).
- A new `precheck-chromium` helper target runs `--version` against
  the installed `chrome-headless-shell`; if it fails to start,
  `make screenshots` and `make render-gist` refuse to run and print
  the exact remedy (`make setup-system-deps` or the equivalent
  sudo command).
- `render-gist.py` now preserves the gist on capture failure and
  prints the URL plus the `gh gist delete <id>` command on stderr,
  so a broken capture leaves the artifact alive for inspection
  instead of vanishing.

## Recurring lessons worth carrying forward

- **Foundational chapters earn more review rounds.** Every later
  chapter inherits Chapter 4's conventions, sanity-check format,
  and tone. The cost of getting them right pays for itself.
- **The line between "polish" and "real omission" is fuzzy.**
  Round 10 caught commutators after nine prior rounds had missed
  them. Iterating past the polish threshold is defensible for
  foundational material, less so for downstream chapters.
- **Source-detectable problems belong in lint; render-visible
  problems belong in screenshot review.** The cheaper layer should
  catch what it can. Every new renderer gotcha discovered through
  screenshots should be encoded as a lint rule so it cannot recur.
- **Verifying renders requires actually reading them.** A
  structural pass at fit-to-window scale ("the section is there,
  the heading is there") is not the same as confirming each
  equation renders. Several inline-`pmatrix` failures survived
  structural passes because raw LaTeX visually resembles dense math
  notation at small scale.
- **Convention decisions are global commitments.** The QFT
  negative-exponent convention obligates every later chapter on
  phase estimation, Shor's algorithm, controlled-phase signs, and
  Qiskit comparisons. Name conventions explicitly so they can be
  referenced later by name rather than re-derived.
- **Cheap, exhaustive test sheets beat narrative reasoning when
  investigating renderer bugs.** Three earlier rounds of bug-by-bug
  diagnosis produced a partly-wrong catalog. One structured test
  sheet with labelled cells overturned two of those diagnoses,
  surfaced a new bug, and produced a single artifact that can serve
  as both internal documentation and an upstream reproducer.
- **Single source of truth, not catalog-by-accumulation.** Five
  rounds of bug discoveries had accumulated into a 170-line gotcha
  section in `PROCESS.md` that partly contradicted itself. A
  canonical memo (`docs/github-markdown-math-bugs.md`) backed by a
  live test sheet is now the single source; `PROCESS.md`, the
  lint, and the upstream-feedback drafts derive from it.
- **Don't delete artifacts on failure.** A capture pipeline that
  drops its inputs in a `finally` clause destroys the evidence the
  user needs to debug. Failure paths should preserve everything,
  with the remedy printed to stderr.
- **Fresh-OS installs are the canonical test for "did setup
  actually capture everything?"** The WSL Ubuntu 24.04 run
  surfaced two prerequisites (`python3-venv`,
  `playwright install-deps chromium`) that a developer machine
  already had quietly installed. Both are now first-class in the
  Makefile.
