## 5. Agile-анализ (уровень CTO)

### Есть ли понимание продукта?
**Частичное.** Команда понимает, что строит compliance/data privacy tool (HIPAA, GDPR). Но: нет чёткого product brief, acceptance criteria приходят устно, требования меняются между созвонами. Нет user stories, нет product backlog в формальном виде.

### Есть ли backlog?
**Нет формального.** Есть Excel/Google Sheet с задачами по спринтам, но это скорее todo-list, чем prioritized backlog. Нет story points, нет estimation, нет definition of ready.

### Есть ли ownership?
**Частично.** Распределение по ролям есть (Микола — бекенд, Олександр — фронт, Наталія — дизайн), но ownership размыт: кто отвечает за product decisions? Кто финально утверждает архитектуру? Міра пытается взять роль координатора, но это не формализовано.

### Есть ли Definition of Done?
**Нет.** Ни разу не обсуждалось. Нет критериев: что значит "задача готова"? Code review? Тесты? Деплой? Утверждение Людмилой?

### Есть ли синхронизация между ролями?
**Слабая.** Дизайн блокирует фронтенд. Бекенд работает параллельно, но без контракта API. Нет API-спецификации, нет contract-first подхода. Решили делать ежедневные стендапы — это хорошо, но пока не запущено.

### Что работает
- Есть рабочий референс-проект (Ігнат) — команда может от него отталкиваться
- Бекенд-темплейт готов (NestJS, структура модулей)
- Фронтенд-темплейт готов (React 19, auth работает)
- Команда мотивирована и открыта к обсуждению
- Решение о кросс-ревью — правильный шаг
- Ежедневные стендапы — правильный шаг

### Что сломано
- **Нет единого product backlog** — задачи в разных файлах, спредшитах, чатах
- **Нет Definition of Done** — никто не знает, когда задача "готова"
- **Нет API-контракта** — фронт и бек работают в изоляции
- **Дизайн — bottleneck** — один дизайнер на весь проект, фронтенд простаивает
- **Requirements management** — информация от Людмилы теряется, противоречива, устная

1. **Создать формальный backlog в Trello** с приоритетами, acceptance criteria, assignees
2. **Договориться о Definition of Done** (code review + работает локально + нет критических багов)

### Технологии

| Слой | Технология |
|------|-----------|
| Frontend | React 19, Vite 7, Tailwind CSS, Framer Motion, Redux Toolkit, i18n |
| Backend | NestJS, TypeORM, MySQL, JWT, Swagger |
| PII Engine | Microsoft Presidio |
| Infra | Docker, docker-compose |
| Auth | Magic Link (email-based, JWT tokens) |
| Export | CSV, JSON, PDF |

### Потенциальные проблемы архитектуры

1. **Нет message queue** — файл-аплоуд + Presidio processing = синхронная обработка? При больших файлах — timeout. Нужен job queue (Bull/BullMQ).
2. **Нет кэширования** — повторные запросы к Presidio будут медленными.
3. **Email-сервис не определён** — Magic Link требует надёжной доставки (Sendgrid? Mailgun?).
4. **Нет error handling strategy** — что если Presidio упадёт?
5. **Нет API versioning** — при двух репозиториях важно контролировать совместимость.
6. **MySQL для compliance** — хранение PII-данных требует encryption at rest; не обсуждалось.

- **Почему важно:** В команде хаос с информацией. Тот, кто структурирует — становится незаменимым.
- **Влияние:** Людмила увидит проактивность; команда будет обращаться к тебе за контекстом.

#### 2. Предложи API-контракт
- **Действие:** Напиши Swagger/OpenAPI спецификацию для первых эндпоинтов (auth, file-upload, wizard). Скинь в чат: "Набросал API-контракт, чтобы фронт и бек не блокировали друг друга".
- **Почему важно:** Никто этого не делает. Это задача уровня middle/senior.
- **Влияние:** Разблокирует параллельную работу, покажет системное мышление.

#### 3. Возьми ownership над конкретным модулем
- **Действие:** Выбери модуль (например, File Upload + Processing pipeline или Presidio integration) и доведи его до конца.
- **Почему важно:** Людмила оценивает командную работу, но также ownership. "Этот модуль сделал X" — конкретный результат.
- **Влияние:** Резюме-буст, уверенность в себе, конкретный deliverable.

#### 4. Пиши тесты
- **Действие:** Добавь хотя бы unit-тесты для своего модуля. Никто в команде об этом не говорит.
- **Почему важно:** На code review Людмила/ментор увидит зрелость подхода. Это то, что отличает junior от middle.
- **Влияние:** Меньше багов на демо, профессиональный имидж.

#### 5. Будь активен в общем чате
- **Действие:** Каждый день: что сделал, что планирую, есть ли блокеры. Короткие сообщения.
- **Почему важно:** Людмила прямо сказала, что следит за активностью в чате. Молчание = "не работает".
- **Влияние:** Видимость, доверие, потенциальный job offer.

#### 6. Не добавляй лишнего
- **Действие:** Людмила предупреждала: прошлые стажёры добавляли "лишние фичи" и результат был хуже. Делай ровно то, что в acceptance criteria.
- **Почему важно:** Overengineering — типичная ошибка junior/middle. Показывает незрелость.
- **Влияние:** Стабильный, предсказуемый результат > "вау-эффект" с багами.

### Ошибки, которых следует избегать

- **Молчать, если что-то непонятно.** Задавай вопросы рано — это не слабость, это профессионализм.
- **Работать изолированно.** Pair programming сессии — ходи на них, даже если не блокируешься.
- **Игнорировать code review.** Давай качественные ревью другим — это учит и показывает вовлечённость.
- **Тратить время на "красивый код" вместо работающего.** 3 месяца — мало. Приоритет: работает > красиво.
