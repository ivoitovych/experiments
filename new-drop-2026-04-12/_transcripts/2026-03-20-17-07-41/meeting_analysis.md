**Тип:** Kickoff-звонок команды интернов  
**Проект:** Healthtech-приложение (анонимизация медицинских данных)  
**Дата:** ~3 недели до старта разработки (30-го числа)  
**Участники:** 9 человек  
**Куратор:** Людмила (представитель компании)

### Блок 4: Технические обсуждения

**UI-библиотека:** Наталья предложила использовать Material UI на 80%, кастомизируя шрифты и цвета. Людмила ранее упоминала, что MUI не очень удобен. Кто-то предложил Tailwind. В документации проекта указаны ограничения по inline-стилям. Финальное решение — уточнить у Людмилы.

**Сервис анонимизации данных:** Написан на Python, но команда работает на TypeScript. Віктор выяснил, что с сервисом можно взаимодействовать через POST-запросы (REST API), без прямой работы с Python.

**Данные и статистика:** Есть страница с чартами (использование анонимизаторов, методы). Нужно собирать статистику — вопрос источника данных открыт.

**Хранилище файлов (blob storage):** Пользователи должны загружать документы (фото, файлы). Вопрос архитектуры хранилища не решён.

**Login/Registration:** В Figma нет страницы логина/регистрации — нужно создавать с нуля. Ігнат и Мира подтвердили, что аутентификация — первый приоритет.

**Task-трекинг:** Ігнат предложил GitHub. Мира согласилась, но нужно уточнить у Людмилы (возможно, Jira).

**Код-стандарты:** Ігнат поднял тему чек-листов, валидации кода, общих правил. Мира попросила его набросать предложение в чат.

## 4. Risks (Риски)

### Организационные

| Риск | Причина | Последствие |
|------|---------|-------------|
| PM без IT-опыта | Мира — свитчер, первая роль в IT | Может не замечать технические блокеры, неверно оценивать сложность задач |
| Никто не знает компанию | Все нашли стажировку случайно, нет инсайдеров | Непредсказуемые ожидания, возможные несоответствия |
| Вся команда — интерны без коммерческого опыта | Ни у кого нет production-опыта | Низкая скорость, архитектурные ошибки, отсутствие best practices |
| Наталья частично недоступна (тайм-зона) | Канада до 1 апреля | Задержки в дизайне на старте, блокировка frontend |
| Слишком много зависимости от Людмилы | Все ключевые решения откладываются до среды | Если Людмила не ответит чётко — команда застрянет |

### Технические

| Риск | Причина | Последствие |
|------|---------|-------------|
| Нет архитектуры проекта | Ни у кого нет системного видения | Несогласованные компоненты, рефакторинг на ходу |
| Непонятен scope (объём работы) | Не определено: по мокапу или свободно | Перерасход времени или недостаточная функциональность |
| Login/Auth не специфицирован | Нет макета, нет требований к данным | Придётся придумывать самим — риск переделок |
| Источник данных для статистики неясен | Чарты есть в дизайне, данных нет | Mock-данные, которые потом могут не совпасть с реальностью |
| Blob storage не продуман | Пользователи загружают файлы, но архитектура не обсуждалась | Поздняя интеграция, проблемы с хранением |

### Продуктовые

| Риск | Причина | Последствие |
|------|---------|-------------|
| Не определён primary user | Наталья задала вопрос — ответа нет | UX-решения без понимания пользователя |

### Что есть

| Аспект | Статус | Оценка |

| Ceremony (ритуалы) | Стендапы запланированы, демо каждые 2 недели | 2/5 |

### Что работает
- Команда открыта к коммуникации, вежлива и проактивна
- Ігнат показывает лидерские качества (подготовил файл, схему, поднимал технические вопросы)
- Стендапы зафиксированы с конкретным временем
- Есть план сбора вопросов для куратора

### Что сломано
- **Нет backlog** — команда не знает, что именно делать
- **Нет архитектуры** — никто не нарисовал систему целиком
- **Нет DoD** — невозможно объективно оценить прогресс
- **Нет техлида** — PM не техническая, а среди разработчиков нет явного лидера с авторитетом
- **Scope не определён** — фичи, границы проекта, приоритеты
- **Нет estimation** — никто не обсуждал сроки по задачам

### Что нужно исправить (в порядке приоритета)
1. **Назначить техлида** — Ігнат лучший кандидат (опыт med-портала, HIPAA, инициативность)
2. **Создать backlog** — разбить проект на эпики → stories → tasks
3. **Определить архитектуру** — компоненты, API, база, деплой
4. **Зафиксировать DoD** — что значит «задача сделана»
5. **Сделать estimation** — хотя бы T-shirt sizes (S/M/L/XL)
6. **Определить branching strategy** — Git flow, PR-ревью

## 6. Архитектура проекта (System Design)

### Что известно из обсуждения

Проект — **healthtech-приложение для анонимизации медицинских данных**. Основные элементы:

- Аутентификация пользователей (login/registration)
- Загрузка файлов/документов пользователями
- Анонимизация данных через внешний Python-сервис (REST API)
- Дашборды со статистикой (чарты использования анонимизаторов)
- Несколько страниц/разделов (по Figma-мокапам)

### Предполагаемая архитектура (Senior-уровень)

```
┌─────────────────────────────────────────────────────┐
│                    FRONTEND                         │
│          React + TypeScript + Material UI            │
│          (+ Tailwind для кастомизации)               │
│                                                     │
│  Pages:                                             │
│  - Login / Registration                             │
│  - Dashboard (charts, stats)                        │
│  - File Upload / Document Management                │
│  - Anonymization Results                            │
│  - Settings / Profile                               │
└──────────────────────┬──────────────────────────────┘
                       │ REST API (JSON)
┌──────────────────────▼──────────────────────────────┐
│                    BACKEND                          │
│              NestJS + TypeScript                    │
│                                                     │
│  Modules:                                           │
│  - Auth (JWT / session)                             │
│  - Users                                            │
│  - Files (upload, storage management)               │
│  - Anonymization (proxy to Python service)          │
│  - Statistics (aggregation for dashboards)           │
└───────┬─────────────────┬───────────────────────────┘
        │                 │
   ┌────▼────┐    ┌───────▼────────┐
   │  MySQL  │    │  Blob Storage  │
   │  (data) │    │  (files/docs)  │
   └─────────┘    └────────────────┘
        │
   ┌────▼─────────────────┐
   │  Python Anonymization │
   │  Service (external)   │
   │  (REST API / POST)    │
   └──────────────────────┘
```

### Технологический стек (на основе обсуждения)

| Компонент | Технология | Статус |
|-----------|-----------|--------|
| Frontend | React + TypeScript | Подтверждено |
| UI-библиотека | Material UI (+ Tailwind?) | Ожидает подтверждения |
| Backend | NestJS + TypeScript | Высокая вероятность |
| БД | MySQL | Упоминалось Миколой |
| Хранилище файлов | Blob Storage (тип не определён) | Открытый вопрос |
| Анонимизация | Внешний Python-сервис (REST) | Подтверждено |
| Task-трекинг | GitHub или Jira | Ожидает подтверждения |
| Коммуникация | Slack (Orange Team) | Подтверждено |

### Потенциальные архитектурные проблемы

1. **Аутентификация** — нет спецификации (OAuth? JWT? Email-подтверждение?). Для healthtech обычно требуется повышенная безопасность.
2. **File upload** — непродуманный blob storage может привести к проблемам с масштабированием и безопасностью медицинских документов.
3. **Статистика** — нужно решить: считать в реальном времени или агрегировать батчами. Для MVP — можно агрегировать при каждом запросе.
4. **HIPAA-compliance** — Ігнат знаком, но команда не обсуждала требования к безопасности данных. Для healthtech это критично.
5. **Нет API-контракта** — frontend и backend могут разойтись без согласованного API-спецификации (Swagger/OpenAPI).

## 7. Что делать мне (как разработчику)

### Конкретные действия для максимального роста

**1. Стань тем, кто создаёт архитектурный документ**
- Нарисуй диаграмму системы (как выше), согласуй с командой
- Это сразу выделит тебя как человека с системным мышлением
- **Почему важно:** PM не техническая, остальные — джуны. Тот, кто формирует архитектуру, формирует проект

**2. Предложи API-контракт (Swagger/OpenAPI)**
- Опиши endpoints до начала разработки: `/auth/login`, `/auth/register`, `/files/upload`, `/anonymize`, `/stats`
- **Почему важно:** Это разблокирует параллельную работу frontend и backend. Это то, что делают мидлы и сеньоры

**3. Настрой CI/CD и линтинг с первого дня**
- ESLint + Prettier + Husky (pre-commit hooks)
- GitHub Actions для сборки и тестов
- **Почему важно:** Это инфраструктура, которую никто другой не сделает. А она экономит десятки часов

**4. Пиши тесты (хотя бы для Auth)**
- Unit-тесты для сервисов, integration-тесты для API
- **Почему важно:** Никто из джунов не пишет тесты. Ты — будешь. Это мидл-маркер

**5. Веди технические заметки**
- После каждого звонка — фиксируй решения, open questions, блокеры
- Если PM не ведёт нормальный backlog — помогай структурировать
- **Почему важно:** Документация — это влияние. Кто документирует, тот контролирует нарратив

**6. Бери ownership за конкретный модуль**
- Например: Auth + User management (или Anonymization integration)
- Доведи до конца: от проектирования до деплоя
- **Почему важно:** End-to-end ownership — главный показатель перехода junior → middle

### Ошибки, которых нужно избегать

| Ошибка | Почему это проблема |
|--------|-------------------|
| Ждать, пока PM раздаст задачи | PM — интерн без техбэкграунда. Инициатива за тобой |
| Писать код без согласованного API | Переделки, конфликты, потеря времени |
| Игнорировать Ігната | Он самый опытный, с ним нужно кооперироваться, а не конкурировать |
| Не задавать вопросы Людмиле | Каждый невыясненный вопрос = неделя потерянного времени |
| Фокус только на коде | Коммуникация, архитектура, документация — это 50% работы мидла |

### Позиционирование

- **Сейчас:** Один из 7 разработчиков-интернов
- **Цель:** Стать go-to person для технических решений (де-факто техлид рядом с Ігнатом)
- **Как:** Инициатива + структура + quality. Не количество кода, а качество решений
