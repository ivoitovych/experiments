## Методологія

Кожна вимога з ТЗ перевірена на покриття у PLAN.md. Результат:
- **OK** — повністю покрито
- **GAP** — пропущено або недостатньо покрито

## 3. Створення оголошення (Розділ ТЗ: пункт 3)

| Вимога | Статус | Деталі |
|--------|--------|--------|
| Зареєстрований продавець може виставити авто | **OK** | `POST /api/listings/` з perm `can_create_listing` |
| Базовий — максимум 1 оголошення | **OK** | Перевірка в бізнес-логіці (7.1) |
| Преміум — без обмежень | **OK** | |
| Випадайка з марками | **OK** | `GET /api/cars/brands/` |
| Якщо марки немає — повідомити адміністрацію | **OK** | `POST /api/cars/brand-requests/` |
| Той самий флоу з моделями | **OK** | `GET /api/cars/brands/{id}/models/` + `BrandRequest` |
| Ціна в USD, EUR, UAH (одна валюта) | **OK** | `currency` choices, `original_price`, `original_currency` |
| Решта валют по курсу ПриватБанку | **OK** | `price_usd`, `price_eur`, `price_uah` |
| Ціни оновлюються раз на день | **OK** | Celery Beat задача |
| Вказувати по якому курсу робили підрахунок | **OK** | `exchange_rate_id` FK до `CurrencyRate` |
| Яку ціну вказав юзер | **OK** | `original_price`, `original_currency` |
| Перевірка на нецензурну лексику автоматично | **OK** | `ProfanityValidator` |
| Якщо чисто → статус активного | **OK** | `status = "active"` |
| Якщо знайдено → пропонує редагувати | **OK** | `status = "needs_edit"` |
| Максимум 3 редагування | **OK** | `edit_attempts` counter |
| Після 3 невдач → статус неактивного | **OK** | `status = "inactive"` |
| Лист для менеджера для перевірки | **OK** | Celery task email |

### Знайдені проблеми:

**ISSUE 1: Дублювання полів ціни**
Модель `Listing` має і `price` + `currency`, і `original_price` + `original_currency`. Це дублювання — вони означають те саме. Потрібно прибрати одну пару. Рекомендація: залишити `original_price` + `original_currency` (ціна юзера), а `price` + `currency` видалити.

**ISSUE 2: FK на CurrencyRate для валютного курсу**
`exchange_rate_id` як FK до одного запису `CurrencyRate` не працює коректно. Один fetch ПриватБанку створює 2 записи (USD та EUR). Якщо юзер вводить ціну в UAH, потрібні обидва курси (USD та EUR) для конвертації. Якщо вводить в USD — потрібен лише курс USD.

**Рекомендація:** Замінити `exchange_rate_id` (FK) на `exchange_rate_date` (DateTimeField) або створити проміжну модель `CurrencyRateBatch` яка групує курси одного fetch-у. Або зберігати конкретні курси як числові поля прямо в оголошенні (`rate_usd_uah`, `rate_eur_uah`).

**ISSUE 3: Відсутність unique_together для CarModel**
`CarModel` має `name` і `brand` FK, але немає `unique_together = ('brand', 'name')`. Можна мати дві однакові моделі для однієї марки.

### Знайдена проблема:

**ISSUE 4: Стандартизація регіонів**
Поле `region` на `Listing` — це CharField без обмежень. Для коректного розрахунку середньої ціни по регіону потрібна стандартизація. Якщо один юзер напише "Київ", інший "Київська область", а третій "Kyiv" — агрегація не працюватиме.

**Рекомендація:** Використати choices з 25 областями України + Київ, або окрему модель `Region` з seed-даними.

## 7. Технічні проблеми в плані

### ISSUE 5: Конфлікт імені `apps/auth/`
Django має вбудований модуль `django.contrib.auth`. Назва `apps.auth` може створити конфлікт імпортів.

**Рекомендація:** Перейменувати на `apps/authentication/` або `apps/auth_app/`.

### ISSUE 6: `django-celery-beat` відсутній в `requirements.txt`
`docker-compose.yml` використовує `django_celery_beat.schedulers:DatabaseScheduler`, але пакет `django-celery-beat` не вказаний у `requirements.txt`.

**Рекомендація:** Додати `django-celery-beat==2.7.0` до requirements.

### ISSUE 7: Відсутність `mysqlclient` або `psycopg2`
Шаблон `may-2024-drf` використовує `mysqlclient`. План рекомендує PostgreSQL і має `psycopg2-binary` — **це OK**, але якщо обрано MySQL, потрібно замінити на `mysqlclient`.

### ISSUE 8: Відсутність тестів у плані
Для оцінки 98-100 потрібна якісна робота. План не містить жодного згадування про тести (unit tests, integration tests). Хоча це не явна вимога, це впливає на якість.

**Рекомендація:** Додати етап з базовими тестами хоча б для ключової бізнес-логіки (profanity filter, currency conversion, listing creation limits).

### ISSUE 9: `APPEND_SLASH = False` не згаданий
Шаблон `may-2024-drf` явно встановлює `APPEND_SLASH = False` для API. План не згадує цю настройку.

### ISSUE 10: Відсутність `__pycache__` та `*.pyc` в `.gitignore`
Шаблон має мінімальний `.gitignore`. План згадує `.gitignore` але не деталізує зміст. Потрібно включити стандартний Python `.gitignore`.

## 8. Архітектурні зауваження

### Зауваження 1: User — FK до Role (не M2M)
План використовує `ForeignKey(Role)` для зв'язку User → Role. Це означає один юзер = одна роль. У контексті автосалонів у майбутньому, юзер може мати роль `seller` на платформі і роль `mechanic` в автосалоні одночасно.

**Поточне рішення працює**, тому що ролі в автосалоні йдуть через `DealershipMembership.role`, а платформна роль — через `User.role`. Це **корректно**.

### Зауваження 2: Пагінація не деталізована
План згадує `core/pagination.py` але не вказує тип пагінації (PageNumberPagination, CursorPagination, LimitOffsetPagination). Для великого навантаження CursorPagination краще.

### Зауваження 3: Caching не розглянутий
Redis є в стеку, але використовується тільки як Celery broker. Для "десятки разів більше навантаження" варто розглянути кешування часто запитуваних даних (список марок, курси валют, популярні оголошення).
