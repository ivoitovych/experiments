# Комплексний аналіз нового дропу — 2026-04-28

## Резюме

Цей звіт аналізує **новий дроп розробки від 28 квітня 2026 року**, який охоплює другий спринт команди Orange та початок планування третього спринту. Дроп містить: оновлені snapshot-и бекенду (`orange_anonymization_be-dev`) та фронтенду (`orange_anonymization_fe-develop`), документ Sprint Demo від 23 квітня, та транскрипції двох мітингів (24 та 27 квітня).

**Загальний прогрес: ~55-60% (з ~25% станом на 12 квітня)**

Команда здійснила **серйозний стрибок у функціональності**. На фронтенді побудований повний 4-кроковий Wizard де-ідентифікації, заповнений Redux store з двома slice (auth + jobs), redux-persist, виправлено TokenPage, реальні користувацькі дані замість заглушок. На бекенді з'явились JobsModule (645 рядків), DashboardModule, інтеграція з Presidio, генерація PDF-звітів, JWT verify flow, повна Swagger-документація.

**Однак є критичні проблеми:**
1. **Presidio integration не працюватиме у runtime** через помилку в ключах конфігурації (читається `'ANALYZER_URL'` замість `'PRESIDIO_ANALYZER_URL'`)
2. **Email service впаде на старті** через аналогічну помилку (`'SMTP_HOST'` замість `'MAIL_HOST'`)
3. **Нуль тестів** — як на бекенді, так і на фронтенді (вже третій спринт без тестів)
4. **Дві конкуруючі JWT guards** з різною формою payload — race condition
5. **Розбіжність entities ↔ migrations** не вирішена з квітня 12
6. **Дашборд та синтетичні дані** залишаються заглушками
7. **Деплой на Heroku досі заблокований** через 2FA Людмили

Sprint 2 demo пройшов 23 квітня (без Ігната). Sprint 3 фокусується на технічному боргу: тестинг, завершення кроку 4 wizard, Presidio конфігурація, GDPR логіка.

### 3.2 Presidio інтеграція — детально

**Так, Presidio інтеграцію побудовано** — це головна доставка Sprint 2 на бекенді. Pipeline працює через `EventEmitter2` для async обробки.

#### Pipeline (jobs.service.ts:63-177)

```
1. Користувач натискає "Run Analysis"
        ↓
2. POST /jobs/:id/run → emit event 'job.run'
        ↓
3. @OnEvent('job.run') processJob() запускається асинхронно
        ↓
4. Маппінг HIPAA-style entity codes (NAME, SSN, PHONE...)
   → Presidio vocabulary (PERSON, US_SSN, PHONE_NUMBER...)
        ↓
5. Якщо framework='hipaa' AND method='Safe Harbor':
   → Розширення до всіх 18 HIPAA ідентифікаторів
        ↓
6. Виклик analyzer:
   POST {analyzerUrl}/analyze
   {text, language, entities, score_threshold}
        ↓
7. Конвертація стратегій (Replace/Redact/Hash/Mask) → Presidio операторів
        ↓
8. Виклик anonymizer:
   POST {anonymizerUrl}/anonymize
        ↓
9. Збереження: anonymizedText, processingTime, analysisMetadata
        ↓
10. 5-хв watchdog timeout → marks FAILED якщо застряг
```

#### Ентітайп маппінг (HIPAA → Presidio)

```typescript
{
  'NAME': 'PERSON',
  'DATE': 'DATE_TIME',
  'SSN': 'US_SSN',
  'PHONE': 'PHONE_NUMBER',
  'ADDRESS': 'LOCATION',
  'EMAIL': 'EMAIL_ADDRESS',
  'MRN': 'MEDICAL_RECORD_NUMBER',         // ❌ не існує в Presidio
  'HEALTH_PLAN': 'US_HEALTH_NUMBER',      // ❌ не існує в Presidio
  'VEHICLE': 'US_PASSPORT',               // ❌ семантично невірно
  'CERTIFICATE': 'US_SSN',                // ❌ невірно
  'BIOMETRIC': 'BIOMETRIC',               // ❌ no-op
  'PHOTO': 'PHOTO',                       // ❌ no-op
  // ...та інші
}
```

#### Стратегії анонімізації (підтримуються)

| Стратегія | Presidio оператор | Опис |
|-----------|-------------------|------|
| **Replace** | `replace` | Заміна на `<TYPE>` |
| **Redact** | `redact` | Видалення тексту |
| **Hash** | `hash` (sha256) | Хешування |
| **Mask** | `mask` | Часткове маскування |

#### Чому Olexandr назвав це "диряво"

З транскрипції 24 квітня:
> *"Працює, але працює так собі. Ну, м'яко кажучи, **диряво**"*

Розуміючи код, причини очевидні:
1. **Конфіг bug** (див. секцію 3.3) — URL завжди undefined у runtime
2. **Невірні маппінги** — як мінімум 5 entity types не працюють
3. **`originalText` не персистується** — поле закоментовано в entity, передається тільки in-memory через event payload. Якщо worker впаде між accept і process — текст втрачено.
4. **`validateInput()` визначений але ніколи не викликається** (jobs.service.ts:241)
5. **Presidio не доступний у production** — `presidio/{analyzer,anonymizer}/Dockerfile` файли є passthrough (1 рядок `FROM mcr.microsoft.com/...`), але ніколи не використовуються в workflow. `docker-compose.yml` запускає їх локально, але Heroku deployment не має шляху до них.

### 3.3 Критичні баги в новому коді

#### 🔴 BUG #1: Конфіг ключі Presidio не збігаються (SHOW-STOPPER)

**Файл:** `src/modules/jobs/presidio.service.ts:22, 55`

```typescript
// Код читає:
this.analyzerUrl = configService.get('ANALYZER_URL');     // ❌
this.anonymizerUrl = configService.get('ANONYMIZER_URL'); // ❌

// Але .env.example визначає:
PRESIDIO_ANALYZER_URL=http://localhost:5001
PRESIDIO_ANONYMIZER_URL=http://localhost:5002

// А configuration.ts визначає namespace:
presidio: {
  analyzerUrl: process.env.PRESIDIO_ANALYZER_URL,
  anonymizerUrl: process.env.PRESIDIO_ANONYMIZER_URL,
}
```

**Наслідок:** URL завжди `undefined` у runtime → axios звертається до `undefined/analyze` → `ServiceUnavailableException` для **кожного** job. **Жоден де-ідентифікаційний запит не виконається.**

**Виправлення (1 рядок):**
```typescript
this.analyzerUrl = configService.get('presidio.analyzerUrl');
this.anonymizerUrl = configService.get('presidio.anonymizerUrl');
```

#### 🔴 BUG #2: SMTP конфіг не збігається (Email service впаде на старті)

**Файл:** `src/modules/email/services/email-sender.service.ts:31`

```typescript
// Код читає:
configService.getOrThrow('SMTP_HOST');    // ❌

// Але .env.example має:
MAIL_HOST=smtp.gmail.com
```

**Наслідок:** `getOrThrow` кидає виключення → application crashes on startup якщо ця сервіс ініціалізується.

#### 🔴 BUG #3: Дві конкуруючі JWT guards з різною формою payload

**Файли:**
- `src/modules/auth/guards/auth.guard.ts` — manual JwtService verify, прикріпляє raw payload `{sub, email}`
- `src/modules/auth/guards/jwt-auth.guard.ts` — Passport-based, прикріпляє mapped object `{id, email}` (з jwt.strategy.ts)

**Конфлікт у контролерах:**
```typescript
// users.controller.ts:27 — використовує:
req.user.id   // Очікує {id, email}

// jobs.controller.ts:54 — використовує:
req.user.sub  // Очікує {sub, email}
```

**Наслідок:** Залежно від того, яку guard NestJS застосовує (а вони обидва зареєстровані), один з контролерів отримає `undefined` для user ID.

#### 🔴 BUG #4: Відсутня міграція для таблиці `jobs`

**Файли:**
- `src/database/migrations/1710000000000-InitialSchema.ts` — байт-ідентичний з 12 квітня
- `src/modules/jobs/entities/job.entity.ts` — Entity визначає таблицю `jobs`

**Наслідок:** У production з `DB_SYNCHRONIZE=false` (як рекомендовано) таблиця `jobs` не буде створена → application crashes при першому запиті до Job repository. Працює тільки тому що `.env.example` має `DB_SYNCHRONIZE=true`.

#### 🟠 BUG #5: `DashboardController` зареєстровано двічі

**Файли:**
- `src/modules/jobs/jobs.module.ts:28` — `controllers: [..., DashboardController]`
- `src/modules/dashboard/dashboard.module.ts:20` — `controllers: [DashboardController]`

**Наслідок:** NestJS може видавати warning про duplicate registration або призвести до неочікуваної поведінки routing.

#### 🟠 BUG #6: `originalText` не персистується

**Файл:** `src/modules/jobs/entities/job.entity.ts:79-81`

```typescript
// @Column('text', { nullable: false })
// originalText: string;
```

Поле закоментовано. Текст передається **тільки in-memory** через `EventEmitter` payload. Міграція має `originalText TEXT NOT NULL`, але entity не бачить це поле.

**Наслідок:** Якщо worker process restart між `POST /jobs/:id/run` та обробкою події → text втрачено, job застрягає у PROCESSING до 5-хв watchdog.

#### 🟠 BUG #7: `validateInput()` визначений, але не викликається

**Файл:** `src/modules/jobs/jobs.service.ts:241`

Метод присутній, але ніде не викликається. Безпекова валідація вхідного тексту не виконується.
