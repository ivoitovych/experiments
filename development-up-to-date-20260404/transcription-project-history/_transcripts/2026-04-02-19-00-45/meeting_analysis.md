## 5. 📊 Agile-анализ (уровень CTO)

### Оценка зрелости

| Критерий | Статус | Комментарий |
|----------|--------|-------------|
| Понимание продукта | 🟡 Частичное | Лендинг + авторизация понятны. Wizard (ключевой flow) — «мы не понимаем, как это работает» |
| Backlog | 🔴 Отсутствует | Таски раздаются голосом на созвоне, нет доски, нет приоритизации |
| Ownership | 🟡 Слабое | Люда — единственный навигатор. Без неё команда не знает, что делать |
| Definition of Done | 🔴 Нет | Ни разу не прозвучало, когда задача считается законченной |
| Синхронизация ролей | 🟡 Слабая | Дизайнер меняет дизайн без уведомления devs. PR ревью нерегулярное |

### Что работает

- Есть ежедневные дейлики — структура есть
- Команда показывает прогресс (демо на звонке)
- Люда даёт контекст и навигирует
- Используется GitHub, PR-flow, Figma — инструменты на месте

### Что сломано

- **Нет доски задач.** Таски распределяются устно, нигде не трекаются. Луїза как PM должна это починить, но она джун и ещё не в контексте
- **Нет стабильного дизайна.** Дизайн меняется между спринтами, devs начинают работу и обнаруживают, что всё поменялось
- **Нет code review culture.** PR с 42 файлами, ревью делает только Люда, вечером
- **Нет автономности.** Команда зависит от Люды в каждом решении
- **Нет Definition of Done, нет acceptance criteria**

### Что нужно исправить (приоритезированно)

1. **Создать доску задач** (Jira/Linear/GitHub Projects) с чёткими статусами
2. **Ввести acceptance criteria** для каждой задачи до начала работы
3. **Стабилизировать дизайн:** дизайн утверждается ДО начала вёрстки, freeze-дата
4. **Установить code review правила:** макс. размер PR, обязательное ревью от 1+ человека
5. **Документировать архитектурные решения** (ADR), чтобы не обсуждать одно и то же

## 7. 🎯 Что делать мне (как разработчику)

### Конкретные действия для максимального роста

**1. Стань тем, кто документирует**
- Создай README для проекта с описанием архитектуры, как запустить, env-переменные
- Задокументируй auth-flow (Magic Link) end-to-end — от клика до верификации
- Это даст тебе репутацию человека, который «держит проект в голове»
- **Почему важно:** в команде джунов тот, кто понимает систему целиком — автоматически лид

**2. Установи code review стандарты (де-факто)**
- Начни ревьюить PR других (даже если не просят) — оставляй конструктивные комментарии
- Делай маленькие, чистые PR (5-15 файлов максимум) — показывай пример
- **Почему важно:** Люда уже жалуется на PR с 42 файлами. Будь антипримером Марка

**3. Возьми на себя infra-задачу**
- Heroku-деплой на 3-й неделе — вызовись первым. Настрой CI/CD (GitHub Actions → Heroku)
- Это навык, который отличает middle от junior
- **Почему важно:** инфра — самый дефицитный навык в команде, Люда сама не умеет

**4. Проактивно разберись с Presidio**
- Не жди, пока «дойдём до этого». Запусти Docker-контейнер локально, пойми API
- Подготовь POC (proof of concept) интеграции backend ↔ Presidio
- **Почему важно:** это «следующий большой блок на пару месяцев» — будь готов раньше всех

**5. Создай доску задач, если PM этого не сделает**
- GitHub Projects — бесплатно, уже интегрирован. Создай колонки: To Do, In Progress, Review, Done
- Переведи устные задачи в тикеты
- **Почему важно:** это PM-задача, но PM — джун и пока не в контексте. Тот, кто починит процесс — получит признание

**6. Задавай правильные вопросы на дейликах**
- «Какой acceptance criteria у этой задачи?»
- «Есть ли API-контракт для этого эндпоинта?»
- «Когда дизайн будет заморожен, чтобы начать вёрстку?»
- **Почему важно:** это демонстрирует middle-мышление. Джуны ждут задач, middle — уточняют scope
