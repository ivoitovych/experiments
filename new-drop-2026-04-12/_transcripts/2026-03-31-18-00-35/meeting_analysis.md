## 4. ⚠️ Risks

### Технические риски

| Риск | Причина | Последствие |
|---|---|---|
| **Backend template сломан** | Микола сетапил, не проверил запуск. Ошибки при клонировании | Блокер для ВСЕХ backend-задач. Ігор взялся пересоздать с нуля |
| **Единственный ревьюер (Люда)** | Ревью только вечером, 1 человек. PR могут висеть днями | Bottleneck. Задержки по всему pipeline |
| **Presidio — никто не работал** | Новая технология для всей команды | Неизвестная сложность интеграции. Потенциально долгий onboarding |
| **Нет CI/CD** | Сервер ещё не выделен | Нельзя деплоить, нельзя тестировать интеграцию |
| **Нет общей среды** | Каждый работает локально, нет staging | Интеграционные баги обнаружатся поздно |

### Организационные риски

| Риск | Причина | Последствие |
|---|---|---|
| **Микола — ghost member** | Не отвечает, не присутствует на митингах, backend за ним | Потеря ownership критического компонента |
| **Дизайнер недоступна** | Наташа в переезде (Канада → Португалия) | Блокер по дизайнам. Команда работает без утверждённых макетов |

| **Джуниор-команда без чёткого ownership** | Все участники — джуны (после курсов GoIT и аналогов) | Высокая зависимость от Люды. Медленный прогресс |

## 5. 📊 Agile-анализ (уровень CTO)

### Оценка зрелости процессов

| Критерий | Статус | Комментарий |
|---|---|---|
| **Понимание продукта** | 🔴 Слабое | Команда не обсуждает user value. Нет user stories. Задачи формулируются как «сверстай страницу» |
| **Backlog** | 🟡 Частично | Есть борда с колонками, есть задачи. Но описания неполные, нет acceptance criteria |
| **Ownership** | 🔴 Проблема | Backend owner (Микола) — ghost. Дизайнер недоступна. Люда = единственный decision maker |
| **Definition of Done** | 🔴 Нет | «Merged» ≠ Done. Нет тестирования, нет staging, нет критериев приёмки |
| **Синхронизация ролей** | 🟡 Частично | Daily есть, но frontend/backend не синхронизированы (frontend ждёт backend). Дизайн ≠ готов |
| **Estimation** | 🔴 Нет | Никто не оценивает задачи. «Завтра закончу» — единственный формат |
| **Sprint cadence** | 🔴 Нет | Нет спринтов, нет planning, нет retro |

### Что работает

- Люда активно управляет процессом: борда, daily, контроль прогресса через демо.
- Команда коммуницирует, показывает работу, задаёт вопросы.
- Марк проявил инициативу: нарисовал диаграмму до начала кода.
- Есть дизайн в Figma (хоть и неидеальный).

### Что сломано

- **Single point of failure: Люда.** Она и ревьюер, и PM, и архитектор, и тимлид. Если заболеет — всё встанет.
- **Нет backend ownership.** Микола не работает, замены нет.
- **Нет Definition of Done.** Никто не знает, когда задача «сделана».
- **Нет приоритизации.** Все задачи одинаково важны = ни одна не важна.
- **Задачи плохо описаны.** Разработчики тратят время на уточнения вместо кода.

### Что нужно исправить (приоритетно)

1. **Решить вопрос с Миколой** — либо вернуть, либо назначить нового backend owner. Это критично.
2. **Написать acceptance criteria** хотя бы для текущих задач. Минимум: что должно быть на экране, какой endpoint, какой response.
3. **Добавить второго ревьюера** или перейти на peer review между разработчиками.
4. **Ввести estimation** (хотя бы T-shirt sizing: S/M/L) для планирования.
5. **Сделать integration checklist** — как проверить, что frontend + backend работают вместе.

### Технологический стек

| Компонент | Технология |
|---|---|
| Frontend | React, Material UI |
| Backend | NestJS (TypeScript) |
| Database | MySQL (local, Docker) |
| Text Processing | Presidio (remote, planned) |
| Auth | Magic Link (passwordless) |
| Design | Figma |
| Task Management | Kanban board (не Jira) |
| VCS | Git (PR → review → merge to develop) |

### Потенциальные архитектурные проблемы

1. **Нет API-контракта.** Frontend и backend разрабатываются параллельно без согласованного API spec (OpenAPI/Swagger). Это гарантирует конфликты при интеграции.
2. **Нет env-management.** Нет `.env.example`, нет описания переменных окружения. Каждый настраивает по-своему.
3. **Presidio — чёрный ящик.** Никто не знает, как интегрировать. Нет документации в контексте проекта.
4. **Нет тестов.** Никто не упоминал тесты. При джуниор-команде это критично.
5. **Нет миграций БД.** Упоминается «создание табличек», но нет ORM-миграций.

### Рекомендации (как senior)

- Добавить **Swagger/OpenAPI** для документации API endpoints. Фронт сможет работать по контракту, не дожидаясь backend.
- Настроить **Docker Compose** файл для всего стека (MySQL + NestJS + опционально Presidio).
- Создать **seed-скрипт** для начальных данных в БД.
- Внедрить хотя бы **e2e тесты** для авторизации.

## 7. 🎯 Что делать мне (как разработчику)

### Конкретные действия для роста

| # | Действие | Почему важно | Эффект |
|---|---|---|---|
| 1 | **Пиши acceptance criteria сам, до начала работы.** Перед тем как кодить — напиши в чат: «Я понял задачу так: ... Правильно?» | Покажет, что ты думаешь как middle. Люда это оценит. Сэкономит время на переделки | Репутация надёжного разработчика |
| 2 | **Делай PR маленькими.** Один PR = одна логическая единица. Не копи код неделю | Маленькие PR быстрее ревьюятся. Люда — bottleneck, помоги ей | Быстрее feedback loop |
| 3 | **Документируй свои решения.** Написал endpoint — добавь README с curl-примером. Сделал компонент — опиши props | В джуниор-команде это делает тебя незаменимым. Это то, что отличает middle от junior | Повышение ценности в команде |
| 4 | **Предлагай решения, а не задавай вопросы.** Вместо «что мне делать?» → «Я предлагаю сделать X, потому что Y. Согласна?» | Снимает нагрузку с Люды. Показывает ownership | Рост доверия, делегирование сложных задач |
| 5 | **Возьми на себя DevOps-инициативу.** Docker Compose, README по setup, CI lint — это то, что никто не хочет делать, но все ценят | В команде явная дыра: setup сломан, инфраструктуры нет | Видимость и impactful вклад |
| 6 | **Изучи Presidio до того, как его попросят.** Запусти локально, пойми API, сделай PoC | Люда сказала «никто не работал». Первый, кто разберётся = go-to person | Экспертиза → рост |
| 7 | **Помогай другим.** Если закончил задачу — помоги разблокировать кого-то | Командный игрок = тот, кого оставляют в проекте и продвигают | Лидерские качества |

### Ошибки, которых стоит избегать

- **Не молчи на стендапах.** Молчание = неопределённость = риск для Люды. Даже если застрял — озвучь проблему.
- **Не делай фичи без согласования.** Ігнат делал фичи по референсам — это рискованно. Всегда уточняй scope.
- **Не жди, когда тебе дадут задачу.** Если ты заблокирован — найди, чем помочь. Напиши тесты. Улучши README. Зарефактори.
- **Не игнорируй Figma.** Верстай pixel-perfect. Это первое, что видит ревьюер.
