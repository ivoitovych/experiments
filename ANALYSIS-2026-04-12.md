# Комплексний аналіз стану проєкту — 2026-04-12

## Резюме

Цей звіт аналізує повний знімок розробки проєкту **Clinical Data De-Identification Portal** (команда Orange) станом на 12 квітня 2026 року. Аналіз охоплює: 9 гілок бекенду, 7 гілок фронтенду, 14 транскрипцій мітингів (19 березня — 8 квітня), Git-правила, правила розробника та порівняння з референсною реалізацією.

**Загальний прогрес: ~25% (бекенд ~30%, фронтенд ~25%)**

Порівняно з попереднім зрізом (4 квітня, ~16%), команда просунулась. З'явились: робочий Magic Link auth flow (бекенд відправляє email), CI/CD pipeline з деплоєм на Heroku, повноцінна сторінка автентифікації (фронтенд), контактна форма, виправлений ProtectedRoute. Але **ядро продукту (Presidio де-ідентифікація) не розпочато**, Redux store порожній, тестів нуль, і на момент останнього мітингу (8 квітня) **нічого не задеплоєно на сервер**.

## 4. Git-правила та правила розробника

### З PDF "Git Rules"

- PR тільки з `develop`, ніколи не пушити напряму
- master/main — тільки для init commit та production
- Видаляти remote-гілки після мержу
- Типи для всіх параметрів, без `any`, try/catch
- Без magic numbers, без хардкоджених значень, без console.log
- Conventional commits, покриття тестами
- **Backend:** Swagger для кожного ендпоінту, ConfigService замість process.env, UUID для PK
- **Frontend:** логіка в хуках (не в компонентах), кольори/шрифти в темі, i18n, абсолютні імпорти
- Скріншоти для візуальних змін
- **3 PR мають пройти ревʼю або роботу треба переробити**

### З картинки "Rules for Developer"

- Git Flow діаграми: master → develop → feature/fix branches
- Hotfixes: від master, мерж назад у develop
- 8-кроковий процес створення проєкту

## 7. Що працює end-to-end

### Magic Link Auth Flow (частково)

```
✅ FE: Користувач вводить email → POST /api/auth/login
✅ BE: Upsert user → генерація JWT → відправка email з magic link
⚠️ FE: TokenPage зберігає токен з URL (але НЕ викликає verify)
⚠️ FE→BE: Верифікація токену не інтегрована
✅ FE: ProtectedRoute перевіряє наявність токену
```

### Contact Form (частково)

```
✅ FE: Форма з валідацією (Yup) → POST /api/email/contact
✅ BE: EmailController приймає DTO → EmailSenderService відправляє email
⚠️ API контракт: DTO поля FE і BE не збігаються (name vs firstName/lastName)
```

### CI/CD Pipeline (працює)

```
✅ FE push → notify-backend.yml → repository_dispatch
✅ BE unified-build.yml → checkout FE+BE → build → deploy Heroku
✅ Parameterized: FRONTEND_REPO, FRONTEND_BRANCH через vars
```

## 9. Аналіз процесу та динаміки

### Що працює добре

- **CI/CD pipeline** побудований професійно — cross-repo triggers, parameterized, Heroku deploy
- **Ігнат проводить проєктні аудити** — єдиний, хто бачить повну картину, ідентифікує системні ризики
- **Git-правила формалізовані** — PR template, conventional commits, чек-лист
- **Конфігурація бекенду еволюціонувала** — від `'get host error'` до strict validation
- **Фронтенд архітектура чиста** — хуки винесені, стилізовані компоненти, i18n

### Що не працює

- **Немає інтеграційного власника** — FE і BE будуються ізольовано, API контракти розходяться
- **PR bottleneck** — Людмила єдиний рев'юер, PR висять 2+ дні
- **Правила не дотримуються** — Git-правила вимагають тести, але тестів 0; вимагають 1 коміт на PR, але порушення частi
- **Scope creep** — Sprint 1 scope змінювався 4 рази протягом одного мітингу
- **Presidio — слон у кімнаті** — ядро продукту ігнорується на користь інфраструктури та UI

### Ризик до демо (12/14 квітня)

Команда має:
- Красивий лендінг ✅
- Auth UI з email формою ✅
- Бекенд що відправляє magic link email ✅
- CI/CD pipeline ✅

Команда НЕ має:
- Працюючого end-to-end auth flow ❌
- Будь-якої де-ідентифікації ❌
- Серверного deployment ❌
- Тестів ❌

**Демо покаже "фасад без будинку"** — красивий UI без працюючої бізнес-логіки.
