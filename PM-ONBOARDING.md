# Вхідний документ для Project Manager

## Вітаємо на проєкті Clinical Data De-Identification Portal!

Цей документ створено для вашого швидкого входження в роль PM на проєкті. Тут зібрано все, що потрібно знати: що ми будуємо, навіщо, де ми зараз, хто в команді, і що робити далі.

---

## Частина 1. Що ми будуємо

### Продукт одним реченням

Веб-платформа, яка приймає клінічні медичні тексти (наприклад, виписки пацієнтів) і **автоматично видаляє або маскує персональні дані** (імена, SSN, дати, адреси, телефони) відповідно до міжнародних стандартів захисту даних.

### Для кого

- Лікарні та клініки, яким потрібно ділитися медичними даними для досліджень без розкриття особистої інформації пацієнтів
- Дослідницькі установи, які працюють з анонімізованими даними
- Будь-яка організація, що обробляє PHI (Protected Health Information)

### Які стандарти підтримуємо

| Стандарт | Регіон | Особливості |
|----------|--------|-------------|
| **HIPAA** | США | Два методи: Safe Harbor (18 фіксованих ідентифікаторів) та Expert Determination (ручний вибір) |
| **GDPR** | Євросоюз | Три рівні ризику: Low / Medium / High — кожен визначає набір сутностей |
| **UK DPA** | Великобританія | Аналогічно GDPR, адаптовано для UK |
| **Swiss FADP** | Швейцарія | Аналогічно GDPR, адаптовано для Швейцарії |

### Як це працює (користувацький потік)

```
1. Користувач входить через Magic Link (без пароля — лінк на email)
         │
         ▼
2. Відкривається 4-кроковий Wizard:
   Крок 0: Обрати фреймворк (HIPAA / GDPR / UK DPA / Swiss FADP)
   Крок 1: Ввести або завантажити текст (CSV, JSON, TXT)
   Крок 2: Налаштувати параметри анонімізації (стратегія, мова, поріг впевненості)
   Крок 3: Переглянути налаштування та натиснути "Запустити аналіз"
         │
         ▼
3. Система відправляє текст на аналіз → Presidio знаходить усі PII сутності
         │
         ▼
4. Система анонімізує текст обраною стратегією:
   - Replace:  "John Smith" → "<PERSON>"
   - Redact:   "John Smith" → ""
   - Hash:     "John Smith" → "a1b2c3d4..."
   - Encrypt:  "John Smith" → "зашифровано"
         │
         ▼
5. Результат відображається на сторінці Results:
   - Оригінал та анонімізований текст поруч (side-by-side)
   - Підсвічування виявлених сутностей кольором
   - Фільтрація по типах сутностей (Chip toggles)
   - Експорт у PDF
   - Аудиторський слід відповідності (Compliance Audit Trail)
         │
         ▼
6. Dashboard показує статистику: скільки документів оброблено, скільки сутностей знайдено
```

## Частина 2. Технічна архітектура (спрощено)

```
┌──────────────────────┐                    ┌──────────────────────┐
│   ФРОНТЕНД           │   HTTP/JSON        │   БЕКЕНД             │
│                      │ ──────────────────► │                      │
│   React 19           │   порт 5173→3000   │   NestJS 10          │
│   Redux Toolkit      │                    │   TypeORM + MySQL    │
│   Material UI 7      │                    │   Swagger /api/docs  │
└──────────────────────┘                    └──────────┬───────────┘
                                                       │
                                            ┌──────────┴───────────┐
                                            │   PRESIDIO (Docker)  │
                                            │   Analyzer  :5001    │
                                            │   Anonymizer :5002   │
                                            └──────────┬───────────┘
                                                       │
                                            ┌──────────┴───────────┐
                                            │   MySQL 8 (Docker)   │
                                            │   порт 3307          │
                                            └──────────────────────┘
```

**Presidio** — це open-source рішення від Microsoft для розпізнавання та анонімізації персональних даних. Працює як два Docker-контейнери:
- **Analyzer** — знаходить PII у тексті (використовує ML-моделі spaCy)
- **Anonymizer** — замінює/видаляє/хешує/шифрує знайдені PII

### Основні модулі бекенду

| Модуль | Що робить |
|--------|-----------|
| **Auth** | Безпарольна автентифікація через Magic Link + JWT токени |
| **Users** | CRUD користувачів, ролі (admin / analyst / viewer) |
| **De-Identification** | Ядро продукту: виклик Presidio, збереження документів, завантаження файлів |
| **Jobs** | Управління задачами обробки (wizard state, статуси, pipeline) |
| **Dashboard** | Агрегація метрик для головної сторінки |
| **Synthetic Data** | Генерація реалістичних фейкових PHI-даних для тестування |

### Основні сторінки фронтенду

| Сторінка | Що робить |
|----------|-----------|
| **Landing** | Публічна промо-сторінка з описом можливостей |
| **Auth** | Форма введення email + верифікація magic link |
| **Dashboard** | Статистика, графіки, список оброблених документів |
| **De-Identify** | 4-кроковий wizard налаштування де-ідентифікації |
| **Processing** | Очікування обробки (polling статусу задачі) |
| **Results** | Результати з 7 інтерактивними функціями |
| **Synthetic Data** | Генерація та перегляд синтетичних даних |

## Частина 3. Команда

### Формат роботи

- **Стажування**, дві команди (Orange і Green) будують один продукт паралельно
- **Спринти**: 2 тижні, 4 години на день на розробника
- **Ментор / CTO**: Людмила — єдиний рев'юер PR, проводить Q&A сесії, ставить вимоги
- **Git Flow**: master → develop → feature branches, PR обов'язкові
- **Правило**: один таск = один коміт = один PR

### Поточний склад команди Orange

| Роль | Хто | Статус |
|------|-----|--------|
| PM | **Ви (новий)** | Входження в роль |
| Попередній PM | Міра (non-IT бекграунд) + Луїза (junior, 2 дні на проєкті) | Передача |
| Frontend lead / Infrastructure | **Ігнат** | Найпроактивніший, рекомендований як техлід |
| Frontend | Олександр | Активний, login page |
| Frontend | Віктор | Layout |
| Backend | Ігор | Перебудував бекенд-шаблон після зникнення Миколи |
| Backend (email service) | Марк | Auth email service |
| Designer | Наталія | Figma, не встигає за темпом розробки |
| Backend (зник) | ~~Микола~~ | Перестав відповідати після дня 1 |

### Відомі проблеми команди

1. **Бекенд-волонтер зник** — Микола перестав відповідати, Ігор підхопив
2. **PR bottleneck** — Людмила єдиний рев'юер, рев'ює тільки 20:00-22:00, PR висять 2+ дні
3. **Дизайнер не встигає** — дизайни змінюються посеред спринту, розробники переробляють
4. **Дисципліна PR** — неодноразові порушення (кілька комітів у одному PR)
5. **Бекло не існував** перший тиждень — задачі з'явились тільки 27 березня

### Що це означає простою мовою

Ми побудували **фасад будинку** (лендінг, тема, layout), але **всередині поки порожньо** — немає автентифікації, немає основної функції продукту (де-ідентифікація), немає зв'язку фронтенду з бекендом. Користувач зараз бачить красиву лендінг-сторінку, може зайти в додаток (без логіну, бо ProtectedRoute не працює), але жодна функція не працює.

## Частина 6. Що робити далі (рекомендований план)

### Негайні дії (перші 2-3 дні)

1. **Познайомитися з командою** — провести 1-on-1 з кожним розробником (15 хв)
2. **Переглянути Trello/дошку спринту** — зрозуміти що заплановано vs що зроблено
3. **Прочитати README проєкту** — він добре описує цільову архітектуру
4. **Подивитися Swagger UI** (`http://localhost:3000/api/docs`) — зрозуміти API
5. **Домовитися з Людмилою** про процес PR review (bottleneck!)

## Частина 8. Глосарій (основні терміни)

| Термін | Пояснення |
|--------|-----------|
| **PHI** | Protected Health Information — захищена медична інформація (імена, SSN, діагнози) |
| **PII** | Personally Identifiable Information — будь-яка інформація, що ідентифікує особу |
| **De-identification** | Процес видалення/маскування PHI/PII з тексту |
| **Presidio** | Open-source інструмент Microsoft для виявлення та анонімізації PII |
| **Magic Link** | Безпарольна автентифікація: одноразове посилання надсилається на email |
| **JWT** | JSON Web Token — токен для авторизації API-запитів |
| **NER** | Named Entity Recognition — ML-техніка розпізнавання іменованих сутностей у тексті |
| **Wizard** | Покроковий інтерфейс (stepper) для налаштування параметрів |
| **Job** | Одиниця роботи: одна задача де-ідентифікації з повним станом wizard |
| **Pipeline** | Послідовність кроків обробки: аналіз → фільтрація → анонімізація → збереження |
| **Safe Harbor** | Метод HIPAA: видалення 18 фіксованих типів ідентифікаторів |
| **Expert Determination** | Метод HIPAA: експерт визначає які дані видаляти |
| **Redux Toolkit (RTK)** | Бібліотека управління станом у React (store → slices → thunks → components) |
| **TypeORM** | ORM для TypeScript — маппінг класів на таблиці MySQL |
| **NestJS** | Backend фреймворк на TypeScript (модулі → контролери → сервіси) |
