## 1. 🧾 Clean Transcript (Читаемая версия)

### Блок 1: Вводная часть и формат работы

Luda открывает сессию как Q&A. Уточняет: все коммуникации ведутся в общих чатах (не в личных сообщениях), чтобы вся команда была на одной странице. Исключение — только для очень личной информации.

### Блок 2: Аутентификация — Magic Link

**Вопрос команды:** Должна ли magic link быть единственным способом входа, или можно добавить Apple/Google sign-in?

**Ответ Luda:** Magic link — это основное требование. Apple/Google — можно сделать как extra, но core-функциональность важнее. Не распыляйтесь на побочные фичи, пока не готов core.

**Как работает magic link:**
1. Пользователь вводит email на странице логина.
2. На email приходит ссылка.
3. Пользователь кликает по ссылке — он залогинен.
4. Нет пароля, нет "забыл пароль".
5. Если письмо удалено или не пришло — просто повторно нажать "Sign in", получить новую ссылку.
6. Нет ограничений по времени на повторный вход. Нет блокировки.
7. При истечении сессии — просто повторный логин через magic link.

**Email-провайдер:** На выбор команды. Можно Google SMTP с логином/паролем (не лучшая практика, но допустимо для стажировки). Если можете сделать лучше — делайте.

### Блок 3: Data Schema и Endpoints

**Вопрос команды:** Нужно ли делать data schema? Можно ли получить список серверных endpoints?

**Ответ Luda:** Да, schema нужна. Но не пытайтесь спроектировать всё сразу. Идите итеративно: берёте фичу → делаете schema → endpoints → frontend. Это и есть ваша работа на 3 месяца. Особенно для джуниоров — маленькие шаги эффективнее.

### Блок 4: Форма "Contact Sales" / "Contact Us"

На лендинге есть кнопка "Contact Sales". Нужно реализовать простую форму: имя, email, сообщение. При отправке — отправлять данные на заданный email. Можно захардкодить email или сделать конфигурируемым. Форма "Contact Us" — та же функциональность.

Это полезно как практика, потому что для magic link тоже нужна отправка email.

### Блок 5: Организация работы и управление backlog

**Рекомендация Luda по организации:**
- Не берите всё сразу. Сосредоточьтесь на одной фиче.
- PM: выделяйте фичу и назначайте одному разработчику (backend + frontend).
- Разработчик сам формулирует подзадачи: schema, backend, frontend, интеграция.
- Так PM проще контролировать: можно кликнуть кнопку и проверить, работает ли.
- Full-stack подход: каждый разработчик ведёт фичу от backend до frontend.

### Блок 6: Библиотеки и лицензии

При выборе библиотек — проверяйте лицензии. Большинство имеют open-source лицензию. Платные часто бесплатны для обучения. Хорошая практика на будущее.

### Блок 7: Frontend — технологии

Команды получили шаблон (Next.js template). Остальное — на усмотрение команды. Если застряли — пишите Luda, описывайте варианты, она поможет выбрать. Ошибки допустимы — это часть обучения.

### Блок 8: Данные пациентов и HIPAA/GDPR

**Суть приложения:** Обнаружение и анонимизация чувствительных данных в документах (имена, email, SSN и т.д.).

**Тестовые данные:** Можно использовать примеры из предоставленных материалов. Строгого формата нет. Важно: система должна находить sensitive data (SSN, имена, email) и предлагать их скрыть.

**Библиотека для де-идентификации:** Python-библиотека (основана на Microsoft Presidio / "Mosaic"), уже упакована в Docker-контейнер. Нужно развернуть на сервере. Luda предупреждает — это может быть bottleneck, т.к. для команды это первый опыт. Если застрянете больше недели — Luda сделает сама.

### Блок 9: Compliance frameworks (HIPAA, GDPR, Custom)

В UI есть выбор compliance framework: HIPAA, GDPR, Custom. Можно выбрать несколько одновременно или создать собственный.

Различия между frameworks существуют, но минимальны (несколько полей). Olga должна была подготовить описание различий, но оно неполное/непонятное. Luda пообещала уточнить и вернуться с описанием.

### Блок 10: Форматы файлов

**Поддерживаемые форматы для MVP:** PDF и .docx.
- PDF — приоритет (в реальности чаще всего используется).
- .docx — вторичный.
- .txt — убрали (никто не использует).
- Excel, JSON — нет.

### Блок 11: Процесс де-идентификации — UX-flow

1. Пользователь загружает документ (PDF / .docx).
2. Система анализирует и находит sensitive entities (имена, SSN, даты и т.д.).
3. Найденные entities показываются пользователю в виде списка.
4. Пользователь может выбрать/снять выбор: что анонимизировать, а что оставить.
5. Каждый entity можно настроить отдельно (per-entity, не глобально).
6. Система может ошибаться (например, принять ID документа за SSN), поэтому финальное решение за пользователем.
7. Confidence threshold — уровень уверенности системы в том, что найденные данные действительно sensitive. При высокой уверенности пользователи обычно выбирают всё автоматически; при низкой — проверяют вручную.
8. "Preserve document structure" — убрать (по указанию Olga).

**Важно:** Де-идентификация НЕ должна быть полностью автоматической. Всегда user validation.

### Блок 12: Методология разработки

**Как работает компания Luda:**
1. Discovery — сбор требований.
2. Разделение на milestones (~2 недели, похоже на спринты).
3. Для ongoing-проектов — более гибкий agile (недельные/месячные спринты, зависит от клиента).

**Для стажировки:** Рекомендуется agile. Даже если оценки будут ошибочными — нужно начать оценивать задачи. Навык estimation важен к концу стажировки.

### Блок 13: Подготовка плана и демо

PM должен подготовить план и представить его Luda (а не спрашивать "что нам делать"). Подход: "Вот наш план, вот что покажем на первом демо, вот что на втором". Клиент не говорит, что хочет видеть — это задача PM.

**Дизайн:** Дизайн должен быть утверждён до начала разработки. Можно отправить Luda на review.

### Блок 14: Пользователи платформы

Primary users: люди, которым нужно анонимизировать данные перед использованием (часто для AI-тренировки). Это могут быть R&D-специалисты, медработники, разработчики — люди с медицинским образованием, но не обязательно практикующие врачи.

### Блок 15: Платёжная система (Stripe)

Не приоритет. Решение о подключении Stripe — после первого месяца, когда будет понятно, справились ли с авторизацией и базовым функционалом.

## 4. ⚠️ Risks (Риски)

### Технические риски

| Риск | Причина | Последствие |
|------|---------|-------------|
| **Деплой Python-библиотеки в Docker — bottleneck** | Первый опыт команды с Docker, серверами, интеграцией чужой библиотеки | Блокировка backend на 1+ неделю. Luda обещала помочь, если >1 недели |
| **Confidence threshold может быть недоступен через API библиотеки** | Фичу взяли из демо, но не проверили API | Придётся убрать или хардкодить |
| **Извлечение текста из PDF — нетривиально** | Разные форматы PDF, сканы, таблицы | Некорректная де-идентификация, потеря данных |
| **Magic link — нетипичный паттерн для джуниоров** | Нет опыта, нет примеров | Затягивание реализации авторизации |

### Продуктовые риски

| Риск | Причина | Последствие |
|------|---------|-------------|
| **Нет чёткого описания compliance frameworks** | Olga не подготовила документацию | Команды не знают, что именно строить. Блокировка проектирования |
| **Figma-макеты ненадёжны** | Сгенерированы AI или скопированы с демо-сайтов, не верифицированы | Разработка по неправильным макетам, переделка |
| **Scope creep** | Много "было бы хорошо" фич (Stripe, PDF, Apple sign-in, add item) | Команда не завершит core |

### Организационные риски

| Риск | Причина | Последствие |
|------|---------|-------------|
| **Нет backlog** | Команды не знают, как его формировать; ожидают указаний | Хаотичная разработка без приоритетов |
| **PM не понимает свою роль** | Спрашивает "что делать на демо" вместо предложения плана | Отсутствие ownership, зависимость от ментора |
| **Две команды делают одно и то же без синхронизации** | Параллельная разработка, разные решения | Дублирование ошибок, невозможность сравнения |

## 5. 📊 Agile-анализ (уровень CTO)

### Понимание продукта — 🟡 Частичное

Команды понимают общую идею (загрузить документ → найти sensitive data → анонимизировать). Но детали (compliance frameworks, confidence threshold, edge cases) не проработаны. Figma-макеты ненадёжны. Описание от Olga неполное.

### Backlog — 🔴 Отсутствует

На момент звонка backlog нет ни у одной команды. PM ожидают, что Luda скажет, что делать. Luda явно просит: PM должен прийти с планом, а не с вопросами. Разрыв в ожиданиях.

### Ownership — 🟡 Слабый

Luda пытается передать ownership командам ("это ваше решение", "вы PM"), но команды не готовы его принять. Много вопросов формата "а нам нужно это делать?", "а это приоритет?".

### Definition of Done — 🔴 Нет

Не обсуждалось. Нет критериев готовности фичи, нет acceptance criteria. Это приведёт к расхождению ожиданий на демо.

### Синхронизация между ролями — 🟡 Формально есть

Есть daily calls (упомянуты), Friday calls, демо. Но содержание не структурировано. На самом звонке видно: PM не знает, что спрашивать; разработчики не знают, что строить; ментор не даёт прямых ответов (намеренно — это обучение).

### Что работает
- Ментор осознанно передаёт ответственность командам — правильный подход для обучения.
- Есть Figma-макеты (пусть неидеальные) — визуальная точка отсчёта.
- Есть работающий прототип (библиотека в Docker) — не с нуля.
- Full-stack подход per-feature — хорошая рекомендация.

### Что сломано
- Нет backlog, нет estimation, нет DoD.
- PM не умеет формировать план — ждёт указаний.
- Документация продукта (от Olga) неполная и непонятная.
- Figma-макеты не верифицированы — могут ввести в заблуждение.

### Что нужно исправить (срочно)
1. **PM:** Сформировать план на первый спринт (2 недели) с конкретными deliverables.
2. **Команда:** Создать backlog хотя бы из 10-15 задач с грубой оценкой.
3. **PM:** Определить Definition of Done для каждой фичи.
4. **Ментор/Olga:** Предоставить внятное описание compliance frameworks.
5. **Команда:** Утвердить дизайн ДО начала разработки.

### Потенциальные проблемы архитектуры

1. **Интеграция Node.js ↔ Python service:** Два разных runtime. Нужен чёткий API-контракт (REST или gRPC). Для джуниоров это нетривиально.
2. **Файловое хранилище:** Не обсуждалось. Где хранить загруженные PDF? Local filesystem? S3? Нужно решить.
3. **Session management для magic link:** JWT? Cookie-based? Не обсуждалось.
4. **Текст-экстракция vs де-идентификация:** Это два отдельных шага. Нужен pipeline: upload → extract text → send to Presidio → show results → user edits → export.

## 7. 🎯 Что делать мне (как разработчику)

### 1. Стань тем, кто первый развернёт Python-сервис

**Действие:** Возьми на себя деплой Presidio Docker-контейнера. Изучи API, напиши обёртку (endpoint на Node.js, который проксирует запросы в Python-сервис).

**Почему важно:** Luda прямо сказала — это bottleneck. Тот, кто решит его первым, покажет инициативу и техническую зрелость. Это также даёт глубокое понимание core-продукта.

**Влияние:** Ты становишься человеком, без которого команда не может двигаться дальше. Это позиция силы.

### 2. Предложи архитектурную схему до начала кодинга

**Действие:** Нарисуй простую диаграмму (компоненты, API-контракты, data flow). Покажи PM и команде. Отправь Luda.

**Почему важно:** Никто этого не сделал. Luda ожидает, но не говорит прямо. Это мышление middle/senior — видеть систему целиком.

**Влияние:** PM будет опираться на твою схему при планировании. Ментор увидит системное мышление.

### 3. Начни с magic link + file upload

**Действие:** Реализуй auth (magic link) и file upload как первые два endpoint. Это foundation для всего остального.

**Почему важно:** Без auth нет пользователя. Без upload нет данных. Всё остальное зависит от этих двух вещей.

**Влияние:** К первому демо у тебя будет работающий flow: логин → загрузка файла. Это конкретный, показываемый результат.

### 4. Делай estimation даже если кажется бессмысленным

**Действие:** Перед каждой задачей пиши: "я оцениваю это в X часов". После — фиксируй реальное время. Веди лог.

**Почему важно:** Luda прямо сказала: "К концу стажировки для меня очень важна ваша способность оценивать задачи".

**Влияние:** К финалу стажировки у тебя будет конкретный навык + данные, которые ты можешь показать.

### 5. Не жди идеальных требований — принимай решения и документируй

**Действие:** Когда Luda говорит "решайте сами" — решай. Пиши решение в общий чат: "Я решил использовать X для Y, потому что Z. Если есть возражения — дайте знать". Если нужно — пиши Luda: "У меня два варианта: A и B. Я склоняюсь к A, потому что... Подтвердите?"

**Почему важно:** Luda явно ценит самостоятельность. Junior ждёт указаний. Middle принимает решения и коммуницирует их.

### 6. Ошибки, которых нужно избежать

- **Не делай "идеальную архитектуру" неделю.** Luda хочет видеть работающий код, а не диаграммы.
- **Не распыляйся на Stripe/Apple sign-in/Excel.** Core first. Extras потом.
- **Не пиши код без утверждённого дизайна.** Luda сказала: дизайн → approval → код.
- **Не молчи, если застрял.** Luda прямо просит: пишите, я помогу. Молчание >2-3 дней — красный флаг.
- **Не игнорируй edge cases.** Luda сказала: "На демо я всегда пытаюсь сломать". Думай об ошибках: что если файл пустой? Что если email невалидный? Что если токен истёк?
